# Paseo 怎样驱动多个 CLI provider（2026-11-25）

> 调研日期为 2026-11-25。核对对象是 getpaseo/paseo 的 commit `465db78ab6a4`，版本 0.17.4，许可证 Apache-2.0。官网 https://paseo.sh 。
> 只读阅读了源码，没有运行它的任何二进制。下文的行号都以这个 commit 为准，以后可能变动。

## 1. 驱动方式：全部用结构化协议，没有抓屏

所有 provider 实现同一个接口 `AgentClient`/`AgentSession`（`packages/server/src/server/agent/agent-sdk-types.ts` 第 745–785 行），提供 startTurn、steerActiveTurn、interrupt、respondToPermission、setModel、streamHistory 等操作。

| Provider | 传输方式 | 要点 |
|---|---|---|
| Claude | 官方 Claude Agent SDK（`@anthropic-ai/claude-agent-sdk` 0.3.326）`query()`，调用本机 claude CLI | 开启 `includePartialMessages`；审批走 `canUseTool`；带 `resume`；中断时不杀后台子代理。启动前先清掉继承来的 `CLAUDE_CODE_ENTRYPOINT`，再显式设置成自己的值 |
| Codex | `codex app-server`，stdio 上的 JSON-RPC | `thread/start`、`thread/resume`、`turn/start`、`turn/interrupt`、`turn/steer`；审批用 `item/*/requestApproval` |
| agy | ACP（`agy acp --disable-telemetry`），以插件形式提供 | 新 provider 默认走 ACP 基类（`@agentclientprotocol/sdk`） |
| OpenCode | `@opencode-ai/sdk`，经 server/SSE | 可以复用用户已有的 server；回合结束靠执行事件加日志对账判断，**明确不用 `session.wait`** |
| Copilot、Cursor、Kimi、Gemini CLI | ACP | 也支持通用的 `extends:"acp"` |

## 2. 会话生命周期

- 状态机：initializing → idle ⇄ running → error / closed。
- 修改 model、effort、mode 时，必须在每个 agent 自己的 "lifecycle lane" 里串行执行。
- steer：Codex 用 `turn/steer`，Claude 往 SDK 的 input 里推消息。中断时，丢弃还没被读走的 steer。
- interrupt 是幂等的。中断结果不明确时拒绝接新工作，避免出现两份状态。
- 多账号：用 provider alias（`extends:"claude"` 加 env），或者分别设置 `CLAUDE_CONFIG_DIR`/`CODEX_HOME`。

## 3. 进程归属和能否跨重启存活

- **headless agent 是 daemon 的子进程，daemon 重启它就跟着死。** `agents.resumeOnStartup` 默认关闭。打开后会用 provider 的 resume 接上原会话，再发一句 "Resume working."。这只是 best-effort，不保证 exactly-once。
- 空闲超过 1 小时，runtime 会被回收，下次 prompt 时再 resume；provider 可以否决回收（`canStopRuntime`）。
- **终端 PTY 放在一个 detached terminal worker 里**：经过二次 fork 挂到 init 下，能扛过 daemon 重启、崩溃和升级。新 daemon 通过 0600 权限的 Unix socket 加 secret 重新连上，并重放屏幕（`docs/terminal-worker.md`）。
- 终端里跑的 TUI agent 靠写入用户 settings 的 hook 上报状态（Claude 用 UserPromptSubmit/Stop/Notification）。

## 4. 统一事件和回合结束

- 统一事件 `AgentStreamEvent` 包括：turn_started/completed/failed/canceled、timeline、permission_requested/resolved、attention_required、background_work。
- 时间线条目分 user、assistant、reasoning、tool_call、todo、compaction 等类型。tool_call 再细分为 shell、read、edit（带 unifiedDiff）、write、sub_agent。
- 回合结束的判定：
  - Claude 以 `result` 为准，另设 `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`，用 `session_state_changed: idle` 兜底；
  - Codex 看 `turn/completed`；
  - 发终态事件之前，先把还在进行中的条目关掉。

## 5. 远程访问

- relay 是零知识的：扫 QR 码配对，拿到 daemon 的 X25519 公钥。
- 加密用 `Noise_NK_25519_ChaChaPoly_SHA256`，带计数器防重放。一旦和某个 daemon 公钥协商过 protected 模式，之后锁定为 protected。
- relay 用 Elixir 写，在单独的仓库 getpaseo/paseo-relay。

## 6. 历史和记忆

- 原生 jsonl 是事实来源。daemon 在内存里保留投影后的时间线，resume 时从原生历史重建。
- 客户端缓存不加密。没有跨会话的记忆系统。

## 7. 对 loom 的取舍

- **借用**：
  - 回合结束的判定细节：Claude 的 `session_state_changed` 兜底、OpenCode 不用 `session.wait`、发终态前先关掉进行中条目；
  - 统一的时间线 schema，作为 `loom hist` L2 的参考；
  - "中断结果不明确就拒绝新工作"的规则；
  - relay 的 Noise 配对方案，留给 fleet 跨机时参考。
- **对照**：
  - Paseo 的 terminal worker 和我们的 holder 思路相同。我们的 holder 更进一步，支持同 PID `execve` 换版、条件写入和从会话出生起的完整日志。
  - Paseo 的 headless 会话不能跨 daemon 重启存活，这正是我们 HOTSWAP-4 要解决的问题。
- **不借用**：
  - 所有逻辑塞进一个巨型 daemon（单个 provider 文件就有 7.5k–8.7k 行）；
  - 改用户 settings 来注入 hook；
  - Claude 走 Agent SDK：功能更全，但多一层依赖。是否迁移，留到角色资格评测时再评估。
- **许可证**：Apache-2.0，可以 vendor 单个文件，需要保留版权声明和 NOTICE。
