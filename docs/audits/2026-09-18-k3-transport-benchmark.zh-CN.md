# Kimi K3 原生 CLI 与 RAH 私聊延迟对照

日期：2026-09-18。用户明确授权测试 OpenCode 中的 Kimi K3，以区分模型、CLI 与 RAH 接入成本。本轮只增加隔离验收脚本和证据，不修改生产代码、正式 Agent 模型、账号或工作台部署。

**结论：OpenCode K3 在本轮 RAH 私聊中更快，但不足以证明 Kimi CLI 有缺陷；RAH 两个适配器都有额外模型往返，延迟 P0 仍未闭合。Claude/OpenCode 不能因功能门禁通过而被宣称没有问题。**

## 条件与边界

- 本机 OpenCode `1.18.30`，精确模型 `kimi-for-coding/k3`、variant `high`；Kimi CLI `0.39.1`，精确模型 `kimi-code/k3`、effort `high`。目录和实际 session/placement 元数据均已核对，没有模型回退。
- 两边配置的基础地址都是 `https://api.kimi.com/coding/v1`，但 OpenCode 使用 Anthropic 兼容协议及现有 API key；Kimi 使用 OpenAI chat 兼容协议及现有 managed OAuth。没有证明同一账户、服务端路由或调度等级，不能称为只改变 CLI 的严格 A/B。
- 原生实验每家独立临时空目录，第一轮新 session，后两轮恢复相同 session，交错串行运行。系统提示、工具集合保留各自原生实现；不以人为统一提示抹掉用户实际使用路径的差异。
- RAH 使用临时 daemon、数据库、Agent 私有目录与 DM；Agent 用户指令及角色一致。每家两轮在同一 Provider session，等当前 Run 正常结束后再发下一题，没有同伴发帖竞争或共享正式 Room 历史。
- 原生计时为启动至完整答案事件，不是首 token；RAH 为 Human 消息落库至 Agent 正式消息落库，不包含浏览器绘制。完整空闲时间另外记录。
- 每个条件只有单次样本，没有控制供应商排队、缓存或系统背景负载。正式用户工作继续运行，没有为了测试中断它。本轮不是 Raft 双边计时，也没有重验长期大上下文、停止恢复或复杂 Task。

初次 pilot 的 OpenCode session 记录为仓库 cwd，因此该组不进入下方主比较。脚本随后显式设置 `--dir` 和 `PWD`，从只读数据库校验实际 cwd 后完整重测。另两次 Kimi 参数冲突发生在模型调用前，单列为脚本准备失败，不能记作模型失败或延迟。

## 实测

原生 CLI，单位秒；日期题明确执行一次 `date -u +%Y-%m-%d`，避免模型猜日期：

| 问题                       | OpenCode K3/high | Kimi CLI K3/high |
| -------------------------- | ---------------: | ---------------: |
| 新会话：只回复“你好”       |            5.735 |           12.754 |
| 恢复会话：读取 UTC 日期    |           13.162 |           15.820 |
| 恢复会话：再次只回复“你好” |            6.444 |            2.803 |

六次答案均符合题意，日期均为 `2026-09-18`；没有超时或重试。Kimi 原生第一轮和第三轮的模型请求分别为 12.099 秒和 2.156 秒，两轮输入缓存命中均超过 90%。这证明存在请求时间波动，不能把第一轮慢全部归因于冷缓存，更不能仅凭一次 OpenCode 更快确定 CLI 有故障。

RAH DM 使用同样的问好/日期核心问题，允许必需的 canonical Worker 通信，并明确不创建 Task、不修改记忆：

| 场景           | OpenCode K3 首次正式回复 | Kimi ACP K3 首次正式回复 | OpenCode 完全空闲 | Kimi 完全空闲 |
| -------------- | -----------------------: | -----------------------: | ----------------: | ------------: |
| 新会话问好     |                   17.077 |                   20.451 |            22.018 |        26.811 |
| 恢复会话查日期 |                   16.879 |                   24.779 |            20.506 |        30.939 |

四次均只发一条正确正式回复，Run 正常退出，没有 Task、hold、重试或额外同伴消费 Activation。正式工作台的数据和模型配置未改动。相比同题原生样本，RAH 本次两条路径均更慢；样本数量不足以计算稳定性能提升率。

## 剩余开销的证据

原生问好只有一次模型请求，日期题两次。**RAH 两家都变为问好三次、日期四次**：

1. 模型先生成 `message-check --startup`，取得规则要求的启动内容和实际问题。
2. 日期题额外生成一次 `date`；问好跳过。
3. 模型生成 `message-post`，答案此时才成为正式消息。
4. 模型收到 post 工具结果，再生成最终收尾；占用执行通道直到 Run 结束。

“三次/四次”是整个 Run 的请求数，包含回复落库后的最后一次，不应全部算作用户等待首条回复的成本。

| RAH 场景      | 模型/assistant step 次数 | 工具执行合计 | 回复后至空闲 |
| ------------- | -----------------------: | -----------: | -----------: |
| Kimi 问好     |                        3 |     0.657 秒 |     6.360 秒 |
| Kimi 日期     |                        4 |     0.700 秒 |     6.160 秒 |
| OpenCode 问好 |                        3 |     0.678 秒 |     4.941 秒 |
| OpenCode 日期 |                        4 |     0.691 秒 |     3.627 秒 |

Kimi 问好三次请求分别等待 8.724、9.983、5.740 秒；日期四次为 10.468、5.274、7.393、5.571 秒。这些时间包含网络、供应商排队、预填和生成，不能进一步捏造拆分。OpenCode assistant step wall time还包含工具执行，证据中有注明，不能直接当作纯模型 API 耗时。

Human 到 Run 创建仅 62–218 毫秒。工具执行合计不到一秒，不能通过优化数据库或 Worker 命令拿回上述多轮等待。

上下文也有差异，但本次不是几十万 token 的老 session：

- Kimi 首请求原生输入 21,250 token，RAH 31,566 token；RAH 恢复后首请求 33,651 token。
- OpenCode 首请求原生输入 3,290 token，RAH 17,528 token；原生工具和提示本身就比 Kimi 少。
- Kimi RAH 两次唤醒输入序列化长度为 50,047 / 1,355 字符，证明前批修复没有再次追加整份规则。它不意味着 Provider 只处理 1,355 字符。

因此，已经修掉的“逐轮重复塞整份 Kimi 规则”与尚未修掉的“读取问题、发帖、收尾仍各需模型决策”必须分开。此次没有出现上一轮频道测试的长记忆维护或同伴消费，不能据此宣布那些场景已修复。

## Raft 依据和下一修复重点

Raft Computer `1.0.32` 的分析材料、URL、hash 沿用[前批修复记录](./2026-09-18-latency-p0-repair.zh-CN.md)。`main.js:836149` 的 `formatConcreteMessagesRuntimeInput` 支持直接注入正文；`:836169` 也有不携带正文的 inbox notice，两者都有实际调用方。不能把 Raft 描述成所有场景都一次模型请求，或不保留原生 session。

本地 `packages/agent-host/src/provider-activation-input.js` 仍统一要求先生成 startup check。本轮测得这一流程同时影响 OpenCode 和 Kimi，后续优化应优先覆盖共同路径：对 Raft 已投递正文的适用场景，在既有 Worker/Kernel 交付 owner 下准备并实际交付本轮消息、完整 memory index 与上下文，减少“先让模型决定读取问题”的往返；必须保留身份、目标读取位置、交付 ACK 与 stale-context hold，不能把 spawn 或文本注入当作已读证明。

同时评估原生持续执行与有限 Activation 的生命周期分离，降低回复后的无效收尾和后续消息排队。不能在任意 `message-post` 后强杀进程，因为它也可能只是任务进度。Kimi 原生 system/role、真实 compaction 与 busy steer 仍按前批记录列为未完成；本轮没有擅自迁移用户 session 或改成每轮新会话。
