# 本机 CLI、RAH 私聊与双边频道延迟实测

日期：2026-09-17，Asia/Shanghai。用户要求拆开比较：本机各 CLI 对 RAH 同 Agent 私聊，RAH 频道对 Raft 频道的回复时间与回复人数。沿用用户认可的现有模型配置进行真实付费测试，未调用 Fable。这不是固定模型矩阵的 release gate。

## 结论

本机 CLI 八次与 RAH 私聊八次最终均回答正确；RAH 私聊只有七次在十分钟观察窗口内回复。Codex 第一题用了 **750.748 秒**，是严重迟到，不能算性能验收通过。新建的双边两 Agent 频道中，两轮各有 **2/2** 位成员回复，刷新后仍可见，未复现 OpenCode 只有动态、没有正式消息的问题。

RAH 私聊八次都比本机直接调用慢。Human 消息落库到首个 RunAttempt 启动只有 0.059–0.235 秒，但后续核验发现 Codex D2 的首个运行属于旧 D1，D2 自己的 Activation 等待了 89.641 秒。其余样本主要等待发生在运行启动之后。具体归因见[后续根因审计](./2026-09-17-latency-root-causes.zh-CN.md)，不能把差值全部归因于框架净开销。

## 实测条件

RAH 正式服务构建 `81a4959c371a1730`，builtAt `2026-09-17T05:11:45.846Z`。四个测试脚本开始时记录同一身份，每次发送私聊前断言身份不变，采样后首次对账（`2026-09-17T06:07:06.960Z`）时 health 仍一致。文档交付前再次检查，服务已变为构建 `2fee59a941746692`；本表保留原采样身份，不代表后续构建的性能结果。没有因本轮测试修改生产实现、重启、提交或推送。

| CLI         | 本机与 RAH 私聊模型                | 推理强度 |
| ----------- | ---------------------------------- | -------- |
| Claude Code | `opus[1m]`                         | high     |
| OpenCode    | `iiiiitoken/gemini-3.8-flash-high` | default  |
| Kimi        | `kimi-code/k3`                     | low      |
| Codex       | `gpt-6-astra`                      | low      |

模型来自当前 Agent policy 与 runtime profile；脚本对绑定、推理强度、可执行文件及空 staticEnv 做断言。Claude 原生结果报告主模型 `claude-opus-5[1m]`，并报告辅助模型 `claude-haiku-4-5-20251001`，不能将未版本化绑定误写为 Sonnet。本轮不是 AGENTS.md 中 Sonnet/Luna/DeepSeek/Kimi high 的标准门禁。

本机 CLI 每题请求新临时 cwd、新会话；后续核验发现 OpenCode 原生 session 的 directory 仍为仓库路径，且使用 `--pure`，不能宣称所有 Provider 均已验证为完全隔离工作区。RAH 使用既有 canonical DM、Agent 身份、角色与记忆规则，运行策略为 prefer_resume。没有清空用户历史或私有记忆。因此模型绑定一致不代表输入上下文完全一致。本机没有 RAH Worker 工具交互；RAH 保留显式读取、交付确认及正式发帖流程。

每个 Provider 的第一题先本机、后私聊；第二题反向。每次开始前等待该 Agent 无活跃执行，上一轮结束后再发下一题。不同 Provider 有部分并行；频道测试时 Kimi/OpenCode 的私聊已结束，但 Codex 的长私聊仍在同机执行。没有独占机器、控制供应商负载或进行统计学重复。

计时口径：本机为进程启动到完整结构化回答，包含 CLI 启动；RAH 为 Human 正式消息落库到 Agent 显式正式消息落库。另用正式浏览器逐个私聊刷新确认 D1/D2 可见，不能把诊断输出或进程退出当作正式回答。

## 本机与私聊

两边使用完全相同问题：D1 问好并只回复 `D1 你好`；D2 计算 `17×19` 并只回复 `D2` 与结果。都明确要求不建任务、不读写项目文件、不修改记忆。完整问题在机器可读证据中。单位为秒。

| Agent    | D1 本机 |     D1 私聊 | D2 本机 | D2 私聊 |
| -------- | ------: | ----------: | ------: | ------: |
| Claude   |   3.615 |      24.506 |   3.390 |  17.029 |
| OpenCode |   4.337 |      36.670 |   4.255 |  34.094 |
| Kimi     |  14.731 |     104.781 |   5.002 |  20.746 |
| Codex    |  23.287 | **750.748** |  92.542 | 115.152 |

八个本机回答和八个私聊回答内容均正确。OpenCode 本机 D2 使用 `D2: 323`，其余 D2 为 `D2 323`；D1 均为 `D1 你好`。

Codex D1 原始观察文件保留 `timedOut: true`，因为十分钟内没有观察到正式回复。结束后从持久化记录及刷新页面复核，找到 13:34:22.340 的回复，距提问 750.748 秒。停止请求在 13:34:28.386 发出，**比回复晚 6.046 秒**，13:34:32.825 完成。停止操作只处理该运行，未强杀其他工作。不能写成“停止促成回复”或“最终无回复”。脱敏证据保留观察超时与事后校正两个事实。

Codex D2 在正式回复前经历两个 RunAttempt。后续核验确认第一个是停止后恢复的旧 D1 Activation（seq 13–13），第二个才是 D2（seq 25–26）；旧激活先运行造成 D2 等待 89.641 秒，自己的运行到回复为 25.511 秒。详情见后续根因审计。

## 频道与频道

双方新建 `latency-pair-0917`，均为一名 Human、两名 Agent。RAH 是 Kimi/OpenCode，Raft 是 Kimi/Alice。每题要求两位各答一次，不回应其他 Agent。两侧发送相差不到一秒，问题与私聊同样是问好、`17×19`。

两边 Kimi 均为 K3，但 Raft 使用默认推理配置，未证实等同 RAH low。Raft Alice 使用 DeepSeek V4 Flash，RAH OpenCode 使用 Gemini 3.8 Flash High。此前真实资料页显示的 Raft Computer 为 1.0.18；没有把它升级到 1.0.32。本轮不能称为同模型、同 Computer 版本基准，1.0.32 发布源码对照见已有修复报告。

| Agent            |       P1 Raft |  P1 RAH |        P2 Raft | P2 RAH |
| ---------------- | ------------: | ------: | -------------: | -----: |
| Alice / OpenCode | 13.065–15.164 |  39.340 |  13.707–15.622 | 50.612 |
| Kimi             | 16.716–75.874 | 110.817 | 19.788–126.204 | 26.560 |

单位为秒。Raft 没有从 DOM 取得秒级持久化时间，区间来自最后未见与首次看见回复的浏览器采样，包含发送动作的时间区间。Kimi 到达所在位置有明显采样空档；保留宽区间，不用中点伪造精确响应时间。尤其 **P2 无法据此判定哪边 Kimi 更快**。表中 RAH 则为精确落库时间，不能直接当作两边相同口径的测速排名。

每轮双方均为两位成员各回复一次。P1 都是 `P1 你好`，P2 都是 `P2 323`。RAH 共四条 Agent 正式消息、Raft 共四条；刷新后每轮各两条仍在。RAH 测试频道任务数为零。此前未配平人数的频道测试保留在旧报告，本轮不混用其结果。

## 阶段证据

1. **首个进程启动很快，但需区分 Activation。** 八次私聊首个 RunAttempt 均在 59–235 毫秒内开始；Codex D2 首个运行实际属于旧题，自己的 Activation 等了 89.641 秒。其余七个样本的主要延迟在运行启动之后，不能由此推广为全部场景都不排队。
2. **Codex 长尾在模型/运行链路。** D1 模型请求信号为 13:21:52.210，首段诊断文本 13:28:17.568，相隔 385.358 秒。13:28:21.223 的 message-check 到 tool-end 仅 0.627 秒；之后到 message-post 开始又隔了 360.397 秒，发帖命令结束只需 0.102 秒。仅凭诊断不能区分供应商排队、网络、模型上下文处理与 adapter 缓冲，但可排除这段时间全部花在本地 message-check/post 操作。D2 本机也用了 92.542 秒，说明不能将全部慢响应都归因于 RAH。
3. **Kimi 首输出等待明显。** D1 模型请求信号到首次 thinking-started 相隔 87.987 秒；D2 私聊总耗时降到 20.746 秒。这不是稳定的固定框架开销。
4. **OpenCode 有多轮交互成本。** D1 依次 check/read/post，再 read 收尾。前三次工具开始到结束分别约 0.678/0.239/0.236 秒，但工具轮次之间约有 10.7 秒、9.0 秒等待。原生同题不需要这些交互。这支持调查工具轮次与模型恢复成本，不支持删除交付确认、因果屏障或把 stdout 自动当成正式消息。

优先级应是：查清 Codex 分钟级无输出与发帖前长等待；拆分 Provider 请求/恢复、首输出、工具轮次的耗时；在现有 Worker/Kernel owner 内评估减少冗余轮次。任何后续优化都须保留显式发帖、单执行通道、因果检查与记忆隔离。此次只完成测量，没有借测速改写业务链条。
