## 真正暴露的失败

1. **Role 的最终结果未交付。** 首轮先向频道发确认，再用
   `#efficiency:message_b8c2...` 当作线程目标。服务明确返回
   `HTTP 404: Thread is unavailable or ambiguous in this Room`。
   Worker CLI 保存本地草稿，却给出“状态 UNKNOWN/CANNOT_CONFIRM、不要重发”的指导。
   模型于是结束，Room 中只有进度确认。这既涉及目标选择，也涉及将明确 404 泛化为
   不确定交付的错误指导；后续修复必须区分请求前置拒绝与网络结果不确定，不能直接放宽重发。
   没有把 CLI 最终文字转发为 canonical Room 消息掩盖问题。
2. **旧 Agent 将只读审查提升为 Task。** 明确禁令下仍 claim/start/progress/submit，
   形成真实 Task 与额外生成。行为已证实，不能凭单次轨迹断言只有某一句 prompt 导致。
   应检查任务触发指令与约束遵从；不修改被审查的网络重启代码。
3. **两轮正常续聊依然约五倍总输入。** 首次输入比原生大，且多两次模型生成。
   需要逐项核对固定系统/工具上下文和 box 通信轮次；不先用截断历史、换新 session 降数字。

此前发现的新实例私有挂载约 30 秒发布延迟仍是独立待修项目。
本轮 Role 显式使用现有 mount，进入 Run 前等待约 0.1 秒，不覆盖也不消除该问题。

## 门禁自身的失败与修正

- 初版两处 HTTP 请求字段不符合协议，均在该组模型调用前失败，保留两次记录。
- 直接新建旧 Agent 会触发自动启动，污染新 session 对照；该试验没有用于配对结论。
  后改用初始化但尚未运行的 Agent，先配置许可模型，再发送审查题。
- 该无效试验的入职消息还唤醒了 bootstrap Agent，发生一次未经许可的
  **gpt-5.5 / low turn（2 次生成，输入 50,506，未缓存 25,162）**。
  这是执行本门禁的助手隔离错误；发现后停止隔离 daemon、保留记录。
  随后加入只供 gate 使用的 stdio 模型围栏，thread/start、resume、fork 必须显式匹配
  `gpt-5.6-luna / low` 才能转发；拒绝测试通过，后续两组经该围栏运行。
  不能把这次调用混入获授权模型的比较数据，也不能声称整个测试始终没有越出模型矩阵。
- 旧 Agent configure 并未改变其既有私有 cwd，导致首次查找文件失败。
  后续 gate 已改为将相同源文件和 AGENTS.md 准备到其真实私有 cwd；本次成本保留，不伪造修正后样本。
- 最终 runner 要求三组相同的显式最终答案前缀与最低正文长度，进度确认不计有效答复，
  仍需人工质量审查。用量及质量失败分开保留；一组失败也不阻止其他组收集证据。
  这些门禁收紧有确定性测试，但没有在本批再次付费重跑整套修改后的 workload。

## 质量判断与下一步

原生和 Role 后两轮都能区分局部函数与端到端流程，未因重启丢失之前结论。
原生 P3 声称撤回“PID 相等即可可信”而前文并未这样断言，属于表述不够严谨；
模型列出的条件风险不视为已验证代码漏洞。Role 首轮交付失败使整体业务验收失败。

下一批先修**有效结论可靠入 box**与**不应建 Task**，再针对重复输入/额外生成优化。
完成一批修复后重新执行同 workload 的原生/RAH 配对，不为每个小改动重跑；
旧 Agent 三轮仍待完整验收，Claude/Kimi/OpenCode 与 Raft 同条件比较仍未完成。
