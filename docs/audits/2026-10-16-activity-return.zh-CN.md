# 动态来源返回与列表位置

本批核对官方 v1.21.16 的 `ThreadsInbox-B_gHqypO.js`（URL/hash见[证据](../evo/evidence/2026-10-16-activity-return/summary.json)）以及冻结源码 `a98ae003246a0360872a77d76dec2fccd0347ef7` 的 ThreadsInbox / useAppNavigate。沿用官方 FSL-1.1-ALv2 通知与 owner 非商用复用授权，原文件不改动。

## 保持的官方行为

桌面单击延迟220ms打开内容槽，双击进入完整聊天；手机点击直接进入完整聊天。直接消息列占主内容槽，频道内再开消息列才有第三列。完整跳转只产生一次路由记录，浏览器返回恢复来源 URL 与筛选，不额外发明“返回动态”按钮。已有这些接线经专项复验，无需重写。

## 修正

官方 `scrollRef → setScrollTop → restoredScrollRef → requestAnimationFrame` 会在数据返回后恢复列表位置；Loom 原来卸载动态页后位置丢失。`useActivityScroll.ts` 结构移植这段逻辑，DiscoveryPage 仍直接使用 raft-ui 的 SearchShellViewport。单一界面位置 owner 按客户端生命周期、workspace、筛选及分页区分；切换筛选或页从顶部开始。仅保存一个 scope 与像素位置，不复制官方 inbox store，不缓存消息或接管业务游标，也不写浏览器持久存储。

## 验证及边界

先用长列表展示夹具、真实临时 Core 消息目的地复现返回滚动失败，再实现。1440×1000 和390×844验证一手势一个历史记录、保留提及筛选、异步列表返回后恢复位置，以及切换筛选回顶部。首次筛选断言早于动画帧，修为等待同一个零位置条件，没有修改期望。原活动专项覆盖频道／私聊／消息列定位、高亮、单击预览、双击、返回、刷新及详情宽度。另运行类型检查、产品构建、79项来源检查和格式检查；不运行全后端或付费CLI。

当前仍使用既有分页：离开后返回会重新读取第一页，不宣称恢复已翻过的全部页。页面刷新会清除临时位置；异步重取使列表内容变化时按浏览器实际高度夹取位置。未补已完成集合查询、上下文菜单等未接能力。真实部署仅做只读动态筛选与页面检查；长列表返回由明确标记的隔离夹具验证，不更改用户真实已读位置。
