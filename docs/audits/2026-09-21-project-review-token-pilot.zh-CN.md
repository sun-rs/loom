# 原生 CLI / Raft / RAH：真实项目三轮审查试验

## 范围与可比性

2026-09-21，用户授权继续真实测试。仅使用 Codex `gpt-5.6-luna/low`；三方原生
`turn_context` 均确认绑定。不是四家 CLI 全矩阵，也不是等历史、等缓存的严格性能排名。

项目为 RAH Git 提交 `5122795d0002e52c03048ac1ef186ea119f908b9` 的三个独立
`git archive` 副本。测试结束后核对 2596 个文件，三份一致且与提交内容相同，没有项目文件修改。
副本没有 `.git`，Raft 首轮误用一次 `git show` 后重新读取，计入实际成本。

- P1：限定三个重启保护脚本，最多跟踪两个直接依赖，最多两个有证据的问题。
- P2：追问最后一次 inspect 与 SIGTERM 之间的竞态，要求区分保证/条件/窗口，纠正误报，给出两个回归用例。
- P3：Raft、RAH 关闭并重新打开浏览器标签后继续讨论，不重新审查，给出最终结论与验收标准。
- 全程要求只读、不修改记忆、不创建任务。没有执行重启或修复被审查项目。

原生 CLI 是新会话，Raft 是已有会话，RAH 首次采用 system-memory 模式的新会话。
各方 cwd/项目级指令不同；RAH 自动读了实际开发目录的 README/docs README，属于产品
当前入口的实测开销，但不能算成相同上下文实验。部分轮次重叠使用同一账号，供应商竞争
没有隔离，不能把全部等待差距归咎调度。后续严格复测应串行、均衡顺序并匹配 cwd/历史。

## Token：以 response_id 去重，而不是累加会话累计账单

原生 `turn.completed.usage` 在本机恢复过程中是会话累计值；直接相加会严重夸大。
本表使用原生 `token_usage_record`，按唯一 response_id 去重，只计测试窗口。
输入总数含缓存；未缓存为 input 减 cached input。输出已包含 reasoning，不再重复加。
缓存写入报告为 0；没有推算价格或声称这些数字等于供应商发票。
中断中未完成请求可能没有 usage，因此原生失败尝试的可见消耗仍可能低于实际。

| 三轮累计（原生包含失败与恢复） | 模型已完成响应 | 输入总量 | 缓存输入 | 未缓存输入 |  输出 |
| ------------------------------ | -------------: | -------: | -------: | ---------: | ----: |
| 原生 CLI                       |              5 |  126,051 |  109,312 |     16,739 | 2,426 |
| Raft                           |             16 |  702,388 |  656,384 |     46,004 | 3,454 |
| RAH                            |             13 |  676,546 |  610,048 |     66,498 | 4,315 |

RAH 累计输入比 Raft 少约 3.7%，但未缓存输入高约 44.5%，输出也更多。
这不是“RAH 已比 Raft 省”，更不能把 67 万输入解读为一条请求装入了 67 万上下文。

## 时间与后台工作

RAH 从 Human 消息提交到 Agent 消息提交；Raft 从浏览器发送动作结束到发送工具成功返回，
因此是近似对照。原生按最终有效答案出现计，不把“我将开始审查”算成完成。

| 轮次 | 原生 CLI                                 | Raft 近似 |      RAH |
| ---- | ---------------------------------------- | --------: | -------: |
| P1   | 240 秒未完成；恢复同会话后约 55.8 秒答复 |   57.4 秒 | 113.8 秒 |
| P2   | 约 44.7 秒                               |   30.0 秒 |  89.7 秒 |
| P3   | 约 30 秒                                 |   25.4 秒 |  42.4 秒 |

原生 P1 在两次读取后没有新的可见输出，达到门禁上限后 SIGTERM，恢复后成功；没有
足够证据区分该停滞是供应商排队、网络还是客户端流异常，不能直接标为限流。
RAH 三个 Run 均正常退出，总运行约 124.3、95.8、48.3 秒；本轮没有新增只读 follow-up。
这不否定之前 busy 追加场景仍存在的冗余 Run。

## 工作量与质量：不能只按低消耗判赢

- 三方最终都能延续此前范围和讨论，没有因页面关闭而丢掉已讨论的问题；Raft、RAH
  三轮各自保持同一 Provider session。原生每轮进程结束后 resume 同一会话，另包含一次超时恢复。
  本轮没有测试正式 daemon/Computer 服务重启。
- RAH 三次 startup 输出均有 system-memory 引用，无完整 MEMORY 重复输出，新传输在
  正式环境生效。工具结果序列约 2227、4346、4930 bytes；增长不能单凭长度归为 MEMORY。
- RAH P1 文件读取工具输出约 45 KB + 22 KB；P2 又读取约 38 KB + 5 KB。
  前者包括 cwd 的 README/docs README，后者继续追踪 launcher/drain；这比 Raft
  P2 不再读项目文件的路径昂贵。RAH 还超出了“最多两个直接依赖”的约束，不能把范围扩张算成质量提升。
- Raft P1 有一次无 `.git` 的失败读取，发送遭 freshness hold 后重试；P2/P3 均主动
  调用 `raft task claim`，页面出现 task #1/#2。发送前“作为任务”未勾选且文字明确禁止，
  因此属于本次实际指令遵从失败。测试未擅自删除这些 Task。
- RAH 没有调用 task claim；三次回复长度与局部文件名准确性仍有瑕疵，P3 写成
  `restart-workbench-guard.mjs`，实际为 `workbench-restart-guard.mjs`。
- 原生第一轮恢复后称备份未包含最后写入会导致“重启后状态落后或丢失”，证据不足：
  successor 使用原 state，并不是恢复旧备份。后续有所收窄，但不能据此确认真实丢数据。
- PID/检查窗口的审查发现是待复现假设，三方对严重程度与可利用条件判断不同；本次
  未跑竞态注入，不能将模型回答升级为已确认产品漏洞。本轮没有顺手实施其建议。

## 对后续修复的意义

平台成本确实存在，但总输入、未缓存输入、生成轮数、读取范围和答案正确性要一起看。
本轮 RAH 相比 Raft 更慢，不能解释为“必然多生成”：P1 是 RAH 5 次、Raft 8 次；
P2 为 5 次/4 次，P3 为 3 次/4 次。模型等待、缓存状态及读取行为共同作用。

下一轮优先固定相同 cwd 指令和历史，串行重跑；随后增加 Claude 和四家矩阵、忙时追加、
服务重启恢复和长会话预算。保留本轮失败，不用新会话或仅成功样本替代。
本轮不证明 90%/100% parity，也不证明真实项目 token 消耗已对齐。
