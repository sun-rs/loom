## 暴露的问题与测量限制

### 新实例首轮存在约 30 秒挂载发布等待

本次从首次消息至 Run 启动为 30.107 秒，之前没有任何 RunAttempt。
新实例默认 `agent_private`，创建时 RuntimeOffer 尚未包含该实例的工作目录挂载。
`daemon-execution-workspace-composition.ts` 从 Kernel 绑定刷新工作目录；
`runtime-offer-publisher.ts` 在发布循环中刷新挂载，
`local-workbench-bootstrap.ts` 默认周期为 30,000 ms。
本次首个 Placement 使用下一次发布的 Offer，而不是创建实例时的旧 Offer。
现行调用点只有启动生命周期与定时刷新，解释了这次首轮启动等待；不是模型限流或 session 丢失。

应优先在现有 owner 上让新实例配置触发及时挂载刷新与 Offer 发布，保留定时恢复。
不要靠降低所有轮询间隔或绕过挂载校验掩盖它。该修复尚未实施，需要先加确定性时序回归。
这是新实例进入第一条业务流程的延迟，优先级高于 fork、Side、全平台记忆等扩展。

### 首轮夹具目录指引有误，不能作为干净速度基准

夹具把源文件放在隔离根下的 `workspace`，实例却使用默认私有目录。
首轮两次相对路径读取失败后，模型在同一隔离根查到实际文件并完成审查，
造成额外查找/读取生成。这是验收夹具问题，不能算成产品必然成本。
没有为了更好数字重跑并丢弃该样本；源文件和实际轨迹均保留。
下次性能门禁须明确选择 `existing_mount` 或给出准确绝对源路径。

本次只有一个实例且 runtime 容量为 1；验证同实例排队，但不构成跨实例并发证明。
也未进行 Raft/原生 CLI 同条件对照、压缩、运行中崩溃、付费绑定故障注入。
不能据此宣称成本已经优于 Raft，或四家 Provider 全部完成验收。
