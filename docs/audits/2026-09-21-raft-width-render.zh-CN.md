# Raft 标准布局宽度与折叠边界验证

## 首轮证据范围（后续官方登录补验见文末）

核对 Raft v1.17.3 发布源码，在隔离 Firefox、Chromium 中加载该版本原始 CSS，
按源码原有容器 class、层级、内联宽度及 `_gt` 宽度选择函数重建最小布局。
这属于结构性布局测试，不是已登录官方完整应用的端到端验收，不包含数据加载、
真实点击与用户 Firefox 的本地偏好。官方测试标签当前停在登录页，未读取或改变
用户 Firefox 的保存宽度。RAH 产品代码没有修改。

[测量数据](../evidence/2026-09-21-raft-width-render.json)记录 312 个基础样本、
96 个竖长窗口样本和 4 组记忆初始化测试。基础样本两引擎宽度一致。
样本使用 100% 缩放、DPR 1、16px 根字号、标准布局、桌面导航条 64px。
表中视口宽度含导航条，各栏宽度不含导航条；高度 844px，特别说明除外。
任务 thread 基础样本只记录不插入侧栏的主布局，审批弹窗尺寸另以源码为准。

来源（发布文件仅分析使用，不进入产品依赖）：

- [主包](https://app.raft.build/assets/index-CyTLLjYb.js)：`Twt`、`_gt`、`jf`、`Swt`、`Cwt`、`Zb`。
- [CSS](https://app.raft.build/assets/index-DLWPJCiz.css)：`thread-layout-container`、`thread-side-column` 容器查询。
- [资料面板](https://app.raft.build/assets/ProfilePanel-1Nuu04-4.js)：`slock:profilePanelWidth` 与 1024px 媒体查询。
- 精确 SHA-256 见测量数据。最小测试的容器组装为本地测试代码，原始 CSS、宽度选择函数及记忆 hook 来自上述源码；不声称完整应用复制。

| ---- | -------------- | ------------------------------- | ------------------ | -------------- | ---------------------- |
| 搜索 | 主内容区全宽   | 560px；视口不足 1024px 时 320px | 320px              | 偏好宽度 400px | 偏好宽度 380px         |

搜索／动态直接将消息列作为搜索结果一级预览时，不因为内容是消息列就触发紧凑；
紧凑条件是额外消息列或人物资料已打开，或视口不足 1024px。

| 保存键                        | 默认 | 拖拽范围                          |
| ----------------------------- | ---- | --------------------------------- |
| slock:sidebarWidth            | 240  | 180–320                           |
| slock:searchPanelWidth        | 560  | 400–720                           |
| slock:searchPanelCompactWidth | 320  | 320–480                           |
| slock:threadPanelWidth        | 400  | 360–max(400, floor(视口宽度×0.6)) |
| slock:profilePanelWidth       | 380  | 300–600                           |

搜索和动态共用宽档、紧凑档保存键，两档各自保存。原始 `jf` hook 用真实 React
服务端初次渲染验证：无保存值为 560/320；分别保存 440/440 后为 440/440；
保存 600/360 后为 600/360；越界保存值 300/900 回退 560/320。
因此记忆能隐藏档位切换的视觉变化，但不会删除断点条件。

## 实测变化

### 搜索／动态两栏，无记忆

| 视口 | 列表   | 正文 |
| ---- | ------ | ---- |
| 1280 | 560    | 656  |
| 1024 | 560    | 400  |
| 1023 | 320    | 639  |
| 768  | 320    | 384  |
| 767  | 不显示 | 767  |

从整页结果进入分栏是第一次变窄；继续缩窗但未跨过 1024px，不会再次缩窄列表。
跨过断点后右正文反而会暂时变宽，这是左栏释放 240px 的结果。

### 搜索／动态：列表＋正文＋消息列

| 视口 | 列表 | 正文 | 消息列 |
| ---- | ---- | ---- | ------ |
| 1280 | 320  | 496  | 400    |
| 1104 | 320  | 320  | 400    |
| 1064 | 320  | 320  | 360    |
| 1063 | 320  | 隐藏 | 679    |
| 768  | 320  | 隐藏 | 384    |
| 767  | 隐藏 | 隐藏 | 767    |

列表已经处于紧凑档，不会再缩一档。正文先缩到 320px，然后消息列由 400px
缩到 360px；剩余正文容器不足 680px 后切换为消息列覆盖正文。
这也纠正“左右绝对不缩、只缩中间”的说法。

### 聊天：列表＋正文＋消息列

| 视口 | 列表 | 正文 | 消息列 |
| ---- | ---- | ---- | ------ |
| 1280 | 240  | 576  | 400    |
| 1024 | 240  | 320  | 400    |
| 984  | 240  | 320  | 360    |
| 983  | 240  | 隐藏 | 679    |
| 768  | 240  | 隐藏 | 464    |
| 767  | 隐藏 | 隐藏 | 767    |

上述数值为默认导航宽度的结果，通用条件是剩余容器宽度至少 680px。
改变左栏记忆值也会改变消息列折叠的窗口阈值。

### 人物资料不是消息列的同一套折叠参数

搜索三栏：1280px 时为 320/516/380，1024px 时为 320/260/380；
1023px 时资料以绝对定位覆盖 639px 的正文区域，列表仍为 320px。
此时正文仍有布局宽度，但被资料覆盖，不等于正文又并排显示了一栏。
聊天在 1024px 时为 240/340/380，1023px 时人物资料覆盖右侧 719px。
资料主要通过 1024px 媒体查询切换，不使用消息列的 680px 最低并排规则。

### 高度也会影响消息列

原始 CSS 要求：横屏，或者视口宽度至少 1280px；同时容器宽度至少 680px，
才并排显示正文和消息列。1280×1400 的搜索三栏仍并排，1279×1400 则覆盖正文，
尽管剩余宽度仍足够。因而只报窗口宽度不足以解释 Raft 的全部变化。
人物资料上述断点不依赖这个横竖屏条件。

## 任务页

标准 `Twt` 对 tasks 路由隐藏普通左列表。任务主列表／看板占剩余主内容区；
打开任务讨论由 `Cwt` 选择 modal，`Zb` 的默认宽度为
`min(960px, calc(100vw - 2rem))`，不是固定右侧 400px。
资料侧栏由共享 ProfilePanel 管理。旧 legacy task 面板另有 380px、320–560px
配置，不能把它混同当前任务审批弹窗；Workspace 网格模式也不在本报告范围。

## 结论与未完成项

用户“打开结果后左侧变窄，再缩窗口没有第二次变窄”的体验，可能来自仍处同一档、
已处紧凑档、两档保存成相同宽度，或 Workspace 模式。默认无记忆两栏在
1024→1023px 有明确第二次切换，已通过两引擎的源码隔离渲染验证。
尚未核实用户 Firefox 的具体保存值、Workspace 开关及在线完整页面点击序列；
不能将隔离渲染样本表标为官方账号端到端实测。

### 官方拖拽与恢复

通过指针拖拽将宽档、紧凑档分别设至可见 440px，随后在 1440、1024、1023px
视口测得列表均为 440px，直接复现“跨断点没有第二次变窄”。
刷新后本次测得保存值为宽档 455、紧凑档 425，与最后可见 440 有少量偏差；
这提示快速拖拽结束时的保存时序可能有差异，但本批未对上游内部状态作进一步
调试，不将具体根因当作已验证事实。宽度记忆确实存在，且宽／紧凑独立。
随后按真实分隔线位置恢复宽档 560、紧凑档 320，在分隔线上完成一次无位移点击
后刷新、重新打开结果，再次测得 560/320，确认原始尺寸已恢复。
用户 Firefox 的偏好未被改动；测试没有发送聊天消息或修改任务状态。

### 退出按钮的附带发现

官方消息列覆盖正文时，哪怕左列表仍显示，已经使用左上返回并隐藏右上 X：

“仍分栏时保留 X，全屏才返回”属于本地产品选择，不能标为这一路径的 Raft 原样行为。
