# Raft / Multica 成熟实现吸收台账

状态：**Active implementation ledger**（2026-08-29）。

本文回答两个必须长期可审计的问题：RAH OS 的每个产品/运行模块来自哪里；面对 Raft、Multica 与本仓库既有实现时，为什么选择复用、结构化移植或保留。它不是授权文本，也不把一次源码阅读写成产品完成证明。

## 1. 总原则

1. 产品目标首先复现 Raft 的可见功能、操作语义和交互合同；已有成熟实现时不另造一套竞争协议。
2. `Room event -> Inbox -> Activation -> RunAttempt -> explicit Room action` 仍是 RAH OS 唯一业务链。Raft/Multica 的 Provider session、Issue 或远端 Server 状态不能成为第二个业务真相。
3. Raft 当前 Web/Computer 源码与 Multica Apache-2.0 源码是本轮主要实现来源。旧 `rah` 不再是架构或业务代码来源；最多只比较不含 Session 语义的纯算法，并重新以 Room/Message 测试定义。
4. “直接复用”只用于来源边界、类型和运行依赖均清晰的模块；编译 bundle 采用结构化移植，禁止把混有第三方依赖、Raft endpoint/cookie 或不可读状态的整段 bundle 直接嵌入生产。
5. 所有移植记录固定版本/commit/hash、原始文件、采用的行为和有意不采用的部分。不能指出来源的新增代码必须明确标为 RAH OS glue 或 canonical owner。

## 5. 当前禁止误报

- Raft token/avatar 的直接复用不等于 Agent 页面 application logic 已直接复用。

- `RoomKind=direct` 或 Chat 页能列出 direct Room，不等于 DM open-or-create 已完成。
- bounded forward catch-up 不等于大历史首屏快速可用。
- 参考 Raft/Multica 后自行重写且没有 source fixture 的代码必须标为 `rah-os-glue`，不能宣称为上游复用。
