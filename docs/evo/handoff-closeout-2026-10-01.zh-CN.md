# 异步交接与纵向验收收口

## 设计先行

P79 已完成六帖、五 Run；精确消费凭据取消了 seq32 的后续通知，作者无自身
Inbox。确认的冗余发生在 A 的同一 Run：发帖后立即 message-read，原地等待，
再次读取，最终尝试不存在的 --after-seq。这不是新发现的 Kernel 重复调度。
第一次源码输出截断造成的重读另计，不归咎于消息 box。

实际读取的普通 `help messages` 解释 @ 唤醒，但遗漏已有高级帮助中的异步
等待语义。常驻协议已有相关约束，说明仍不能保证模型遵从。本批最小修法是
统一帮助的语义，不新增控制器、队列、状态、读取限流或自动 final。

所有权：AgentHost Worker 帮助说明工具使用；Kernel 继续独占投递/ACK/调度。
交接后完成其他当前工作再结束本轮；之后被点名的回复会重新唤醒。
历史查询仍可用。普通 post 仍只发布，不能根据 @ 或正文推断工作已经完成。
不把局部帮助修复说成固定代码强制消除了轮询。

## 验证顺序

1. 通过真实 Worker help 门面，先复现普通帮助没有异步交接说明；修复后断言
   包含再唤醒、结束当前工作和不轮询语义，保留发布不结束与长度约束。
2. 完整免费检查。核对活动工作，安全备份重启，再检查真实控制台。
3. 有界真实双实例六帖复测：同 P79 任务、低 effort、无救场补跑；记录消息、
   原生 session、Run、自己触发自己、轮询及用量。失败保留，不用硬终止伪造成功。
4. 当前候选版本经简易 UI/API 验收私聊排队、记忆开关及安全重启续聊。
   产品功能、模型遵从、效率预算和部署结果分别报告；不要求模型永远正确。

Jev 结论见 [研究取舍](jev-research-decision.zh-CN.md)。

## 实施与真实结果

提交 `137186a`，只修改普通帮助卡与回归测试；协议摘要和调度不变量不变。
复现测试先失败、修复后通过。完整 check、format、diff 通过；两次安全重启
均备份完整状态，第二次之后逐表旧行哈希保留。无前端产品代码修改。

### P85：自主交接未通过

### P86：基础贯通通过，效率未验收

新频道、两个独立 Codex gpt-6-luna/low（不代表四家重新验收）：

- API创建 Role/实例/频道，分工审查与下一轮互相引用完成。
- A频道运行中发送私聊；私聊在频道轮结束后执行，共享原session，B无私聊投递。
- A显式写入频道记忆，B通过工具读回；B读关闭后Worker实际403，随后恢复继承。
- daemon安全重启后A仍用原session续聊，未重读文件，能复述前文；B重启后真实执行未测。
- 当前真实Chrome已查看频道、点击进入私聊、重启后重新加载；记忆、历史、空闲状态可见。
  RunAttempt与用量通过控制台模型及同一API核对，不声称逐个表单按钮均点过。

共12 Run、46次生成，942,363累计输入、864,256缓存、78,107未缓存，逐Run
与原生记录一致；单次生成最大输入30,815，累计输入不是单次上下文大小。
没有原生对照，不据此宣称§6通过。预算12次用尽，未补跑。
[证据、原生核账与脚本](evidence/2026-10-01-console-vertical-closeout.json)。

剩余的额外工作必须保留在结论里：

1. 首轮A遇到B先回复的freshness hold后未发出草稿即退出，未ACK，因此同一
   Activation重试，随后send-draft发出；这是保护未交付工作的重试，不是重复通知。
2. B引用记忆作者时使用完整@A，按已裁定规则唤醒A，多出一轮复述。当前合同
   保留署名式@唤醒；不能靠自然语言猜测或Jev取消它。
3. 记忆首次使用有help/list及一次漏turn参数的失败调用；工具使用成本仍有空间。

自动脚本将有明确接收人的后续回复标为有效peerHandoff，不等于有用工作。
人工结论只接受功能路径通过，保留协作可靠性与效率失败。

## 下一步优先级

先核清并减少“被hold后如何完成原交付”的工具路径成本，不能取消ACK/新鲜度
守卫，也不能发帖即强制终止。然后设计“引用身份”与“明确交接”的确定性表达，
同时保留当前@合同，若要改变其唤醒语义须owner裁定；不是新增场景调度器。
不要再用每次漏接力就追加一条提示词作为可靠性方案。

当前足以进行窄前端映射设计，但不能宣称自主多实例协作已验收；本批未开始
phase 4，也未引入fork、side或Jev产品层。

## P86 暂存恢复追查

已确认：`worker-target-context.ts` 的发送窗口把模型提交的旧序号作为新鲜度
下界的限制；`worker-held-send.ts` 的修改稿示例保留这个序号。因此，模型读过
暂存通知后按示例修改正文，仍可能再次暂存。现有 Kernel 回归已覆盖此路径：
随后显式 `--send-draft` 可以发布，且 ACK 仍只到原投递序号。

不能直接把示例中的序号换成服务端最新值：那会把“呈现了新消息”变成模型
确认了更大的范围。也不能后台代发保存的正文；新消息可能已经使草稿失效。
本批保留这些边界，没有新增修订草稿 API 或隐式确认规则。

最小改动限于异常输出：明确暂存不等于完成；修改稿再次暂存时须先审阅新
通知，再决定是否发送；确实无需回复时给出带原 turn 句柄的 `message-check`
命令，并说明该命令不发布草稿、不完成 Task。常驻提示词、协议摘要、Kernel
调度和 ACK 均不改。这是恢复说明缺口的修复，不是强制模型一定完成交付。

测试先复现缺少恢复说明，再验证 CLI 门面输出及原有 Kernel 最终回复边界。
P87 获 owner 单批授权后完成；P85/P86 的失败与效率未验收结论不因此改变。

### P87：恢复样本通过，审查质量失败

产品提交 `672d6ec`；完整 check、format、diff 通过，安全备份重启后真实 Chrome
重新连接，原有消息、Role、实例、记忆及事件旧行哈希不变。

两个新 Codex gpt-6-luna/low（0.158.0）并行审查 P86 的 receipt/PID 固定快照。
最多授权4 Run，实际2 Run、各一帖、两个 Activation completed、零自身 Inbox、
无额外重试。B 首次暂存后按旧序号修改正文再次暂存，随后显式 send-draft，
在同一 Run 交付；原生输出确认收到了新恢复说明。两位自然空闲20秒后只急停
这个验收频道，没有补跑，也没有 Human 救场。

A 7次生成，B 10次，共17次；278,354累计输入、227,584缓存、50,770未缓存；
峰值单次输入20,663。账本与原生逐Run一致，无usage gap。多次重复源码检索、
A读取工具帮助、B主动startup check仍在；没有原生同题对照，不能说效率达标，
也不能把本次恢复成功归因于这几行提示。

质量必须判失败：A声称rename替换后仍保留旧文件0644权限，B在暂存通知里
看见A的观点后也改成同一错误说法。对同一快照做免费临时目录反例验证：先建
0644回执，再执行writeLaunchReceipt，结果为0600。这不是源码缺陷；模型把
错误结论称为“已证实”，且同伴回复放大了错误。不能为了多Agent一致而接受。

[完整证据、工具调用与反例](evidence/2026-10-01-held-recovery-p87.json)。
本批只闭合异常恢复说明并验证一次路径，不宣称自主协作或工作质量已验收。
后续应把调度交付、语义正确与原生效率分别验收；先使用可独立验证的事实与
反例评估协作质量，不在daemon加入场景专用审查流程或自动采纳同伴结论。

### P88：原生 CLI / 本地 Markdown 对照

Owner 提出用纯 CLI 判断问题是否来自 Loom，并授权尝试。本批使用两个新的
Codex 0.158.0 / gpt-6-luna / low session，各两轮，上限4轮全部用尽、不补跑。
沿用 P87 三文件 SHA 和 A/B 分工，保留只读审查与区分事实/风险的角色要求；
只允许写回复 Markdown。没有 Loom daemon、Worker 工具、Kernel、暂存或 ACK。
使用 CLI 原生 app-server 驱动，不是直接请求模型 API。原生记忆及个人 MCP
仍按同一启动隔离关闭；两个 session 的第二轮分别续接自身历史。

先各自读 `box/human.md` 并写独立结论，再将 P87 的真实同伴回复回放为
Markdown（仅替换源文件绝对路径），要求复核并写最终结论。不是让两位重新
自由讨论，也没有让自己的写入触发读取。A/B 顺序执行；B的独立轮只读取
Human与源码，未读取A回复。P87是并发暂存中收到同伴意见，这里是显式复核
轮，且权限配置为workspace-write，因此不是仅替换消息传输的严格消融实验。

四轮共18次生成、258,596输入/220,928缓存/37,668未缓存，精确模型/effort
经原生turn_context核对，四份回复文件均交付，快照哈希不变。首请求均8,995
输入；原生A也进行了额外调用，包括不在Git仓库中的`git status`失败。
调用数不能全部视为浪费：A的权限实验为正确拒绝同伴结论提供了证据。
不能用本批四轮总量除P87两Run总量来宣布效率改善。

**确认的结果：**

- A独立轮未声称权限缺陷；看到错误同伴意见后用真实本地实验得到0600，明确
  拒绝错误机制，保留PID复用的条件性风险。
- B独立轮没有权限观点；回放后称同伴权限问题“有依据”，仅将其降为条件性
  风险，没有识别出即便旧文件确为0644，rename替换后仍变为0600。因此该观点
  依然错误，但不能夸大为与P87完全相同的“已证实缺陷”。
- B同时修正了自己原先对undefined PID的过强判定。免费函数级复现确实可让
  两边undefined相等通过，但这份快照没有调用方，不能证明产品可触发。
- 故同伴错误采纳在无Loom的原生CLI中也会发生；两个样本表现不同，不能声称
  模型必然跟随同伴、不能量化发生概率，也不能据此证明Loom提示毫无影响。

**决策：停止以单次审查答错为理由堆叠调度/提示词修复。**

平台继续负责可确定验证的投递、ACK、隔离、续聊和避免重复运行；这些可以
也必须靠代码保障。额外工具使用要与原生同题路径拆开比较：P87的help/check、
两次暂存往返属于平台接口成本候选，源码检索与验证属于工作路径，不是一律
应该删掉的轮次。权限判断正确性用独立事实/反例评价，不能要求daemon替模型
裁决，也不应以“原生也错”为理由放弃已有额外成本问题。

后续修改须有具体可复现的接口缺陷或固定调度证据；没有此类证据时，保留模型
能力限制，不新增场景控制器。未来效率验收应预冻结等价交付与轮数；模型质量
和平台额外成本分开判，避免为一次偶然答错无限循环付费复测。
