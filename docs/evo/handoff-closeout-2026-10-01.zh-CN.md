# 异步交接与纵向验收收口

## 设计先行

P79 已完成六帖、五 Run；精确消费凭据取消了 seq32 的后续通知，作者无自身
Inbox。确认的冗余发生在 A 的同一 Run：发帖后立即 message-read，原地等待，
再次读取，最终尝试不存在的 --after-seq。这不是新发现的 Kernel 重复调度。
第一次源码输出截断造成的重读另计，不归咎于消息 box。

实际读取的普通 `help messages` 解释 @ 唤醒，但遗漏已有高级帮助中的异步
等待语义。常驻协议已有相关约束，说明仍不能保证模型遵从。本批最小修法是
统一帮助的语义，不新增控制器、队列、状态、读取限流或自动 final。

所有权：AgentHost Worker 帮助说明工具使用；Kernel 继续独占投递/ACK/调度。
交接后完成其他当前工作再结束本轮；之后被点名的回复会重新唤醒。
历史查询仍可用。普通 post 仍只发布，不能根据 @ 或正文推断工作已经完成。
不把局部帮助修复说成固定代码强制消除了轮询。

## 验证顺序

1. 通过真实 Worker help 门面，先复现普通帮助没有异步交接说明；修复后断言
   包含再唤醒、结束当前工作和不轮询语义，保留发布不结束与长度约束。
2. 完整免费检查。核对活动工作，安全备份重启，再检查真实控制台。
3. 有界真实双实例六帖复测：同 P79 任务、低 effort、无救场补跑；记录消息、
   原生 session、Run、自己触发自己、轮询及用量。失败保留，不用硬终止伪造成功。
4. 当前候选版本经简易 UI/API 验收私聊排队、记忆开关及安全重启续聊。
   产品功能、模型遵从、效率预算和部署结果分别报告；不要求模型永远正确。

Jev 结论见 [研究取舍](jev-research-decision.zh-CN.md)。

## P86 暂存恢复追查

已确认：`worker-target-context.ts` 的发送窗口把模型提交的旧序号作为新鲜度
下界的限制；`worker-held-send.ts` 的修改稿示例保留这个序号。因此，模型读过
暂存通知后按示例修改正文，仍可能再次暂存。现有 Kernel 回归已覆盖此路径：
随后显式 `--send-draft` 可以发布，且 ACK 仍只到原投递序号。

不能直接把示例中的序号换成服务端最新值：那会把“呈现了新消息”变成模型
确认了更大的范围。也不能后台代发保存的正文；新消息可能已经使草稿失效。
本批保留这些边界，没有新增修订草稿 API 或隐式确认规则。

最小改动限于异常输出：明确暂存不等于完成；修改稿再次暂存时须先审阅新
通知，再决定是否发送；确实无需回复时给出带原 turn 句柄的 `message-check`
命令，并说明该命令不发布草稿、不完成 Task。常驻提示词、协议摘要、Kernel
调度和 ACK 均不改。这是恢复说明缺口的修复，不是强制模型一定完成交付。

测试先复现缺少恢复说明，再验证 CLI 门面输出及原有 Kernel 最终回复边界。
P87 获 owner 单批授权后完成；P85/P86 的失败与效率未验收结论不因此改变。

后续修改须有具体可复现的接口缺陷或固定调度证据；没有此类证据时，保留模型
能力限制，不新增场景控制器。未来效率验收应预冻结等价交付与轮数；模型质量
和平台额外成本分开判，避免为一次偶然答错无限循环付费复测。

## 暂存修订往返：确定性复现与实施设计

本节只处理可复现的平台接口成本，不处理模型审查结论真伪。

### 已核实的原因与边界

在 `02192ea` 上运行六个相关测试文件，29项通过；另在临时目录复制
`run-attempt-final-reply.test.ts` 的两条修订测试，将原有条件恢复分支前补上
“修订必定再次held”的断言：默认路由与显式target路由均复现。模型原确认
序号为3，首次暂存展示到8；无第三条新消息，修改正文后仍再次held；显式
send-draft才能发出，最终确认仍为3。没有修改产品、正式状态或运行付费CLI。

源码依据：

- `packages/agent-host/src/worker-held-send.ts` 的修订示例保留原replyIntent
  的basedOnRoomSeq/final；这是避免丢失原回复义务所需，不可直接删除。
- `packages/kernel/src/worker-target-context.ts` 的 `#resolveSendWindow`
  使用 `min(input.basedOnRoomSeq, stored)`；普通修订仍走compose，因此旧序号
  继续限制freshness。默认路由也保留原投递范围。
- `packages/kernel/src/held-message-drafts.ts` 已分别存储
  `seen_up_to_seq` 与 `reply_based_on_room_seq`/`reply_final`；前者与后者
  不能互换。`settleHeldDraftReplyIntent` 只在成功发布后处理确认。
- `packages/protocol/src/worker-message.ts` 明确拒绝sendDraft携带正文。
  当前没有“显式确认已展示上下文并修订此稿”的单次调用。

因此第二次hold不是重复Activation，而是接口缺少这种显式动作；原保护仍按
现有合同执行。P87多出的两次失败post中，只能预计省掉修订时这一次，首次
出现新消息后的hold仍有意义。减少一次Worker往返不保证必然少一次模型生成。

### 最小实施方案

单一所有者仍为Kernel的现有消息事务；不增加队列、调度器、自动发帖或
后台判断。沿用同一个Worker消息接口，增加明确的草稿修订动作
（候选CLI形式 `message-post --revise-draft <heldDraftId> --target …`，正文由
stdin提供）。只在暂存错误输出中展示，不增加常驻规则。

1. 必须指定错误回执中的**确切草稿ID**，不能解释为“随便取这个目标的最新
   草稿”。校验认证实例、Room、Thread、同一Activation、有效执行围栏和TTL；
   首版跨Activation修订拒绝，原send-draft跨轮恢复路径保持原行为。
2. 该显式修订动作表示选择针对该稿的已展示上下文重写回复。新鲜度上限来自
   这份草稿冻结的seen_up_to_seq，不取当前Room head或其他读取推进的位置。
   暂存通知仍是有界上下文，不宣称所有正文被完整读过。
3. ACK及final意图保留该稿原来的模型标记；不扩大到seen_up_to_seq，不ACK
   Inbox，不完成Task。普通compose/progress不隐式继承任何草稿意图。
4. 没有再来同目标新消息：原子发布修订正文并解决旧草稿；新消息在首次hold
   之后到达：保存修订稿并返回新的hold，仍需模型审阅，不能自动重发。
5. 不原地覆盖旧稿正文后套用“发送未修改草稿”逻辑。幂等身份包含原草稿ID
   和修订内容；相同请求丢响应后重试必须返回同一事件/新hold。查幂等结果
   先于“原稿已解决”拒绝；同键不同正文冲突。原草稿与新稿保留可追溯关系。
6. 首版仅改正文，附件和附件评论目标从原稿沿用；禁止在这个动作里另行换
   附件、换房间/线程或指定anyway，避免把窄修复扩成草稿编辑系统。

单纯删旧basedOn、换成最新序号、放宽所有普通post的新鲜度、将两个命令
自动串起来，均不采用。它们可能扩大确认范围，或让模型没机会审阅第二次
hold里的真正新消息。

### 必须先失败后通过的验收

- 两条Worker入口：首次hold→明确修订→无新消息时直接发布；ACK仍停原序号，
  final只在发布后出现；对Task与Inbox无完成副作用。
- 修订前第三条同目标新消息到达：再次hold，无消息发布、无ACK；别的线程
  不误阻断，跨私聊/频道和跨实例/Activation不借用草稿范围。
- 相同修订重试只有一条消息；同键异正文冲突；旧稿被替换或过期不误修新稿；
  已成功的重放不因旧稿已解决而丢失成功结果。
- 普通post与send-draft现有行为不变；终止/移除后写入拒绝；原稿附件保留。

设计阶段只证明当前额外往返及给出候选实现边界；后续实施结果见下节。
下一实施批按这些外部行为写失败测试，再最小落地；完成免费检查后安全部署。
真实效率收益需要另行授权的有界复测，本轮不以设计代替门禁通过。

### 实施收口：明确修订原回复草稿

已按上述设计实现共享Worker动作 `message-post --revise-draft <heldDraftId>`，
只在按需恢复输出/高级帮助中出现。四家CLI共用，不增加常驻提示词或模型规则。
Protocol增加`reviseDraftId`，Kernel复用现有消息事务和原草稿附件；没有新队列、
新状态表或数据库迁移。Room消息事件的`revisedDraft: true`区分修订与原样重发，
避免同一幂等键被不同动作复用；原有历史事件不带此字段，保持旧语义。

首版有意收窄：要求同实例、同Activation、同原始Room/Thread，原稿携带模型
的`reply_based_on_room_seq`；CLI/API拒绝覆盖序号、final、附件及anyway。
目标确认稿的`seen_up_to_seq`不代表展示过新鲜度通知，不能拿来优化；没有
原回复标记的稿仍保留普通compose/send-draft路径。此约束避免新增持久证明
字段，也不把不存在的展示当确认。当前Role实例只在自己的执行Room回复。

已验证的自动化行为包括：两条入口无新消息时一步修订发布；第三条新消息
到达时再次hold；ACK不扩大；progress保持非final；同请求成功/暂存重放；
同键异正文/异动作拒绝；过期/已解决/外来Activation/错误目标/终止执行拒绝；
线程与附件保留；真实Worker HTTP门面重放只生成一条消息。TDD先观察旧接口
拒绝reviseDraftId及CLI不认识参数；另先复现修订键误当原样重发的缺口再修。

本节实现不改变首次hold策略，不认为模型审查正确性因此提高。真实CLI收益
未复测；免费测试证明少一次确定的工具往返，不证明必然少一次模型生成。

### Task 后端切片：研究与待裁定设计（2026-10-01）

一手参考（2026-10-01 查阅）：

  显式任务定义描述、预期输出和执行者；适合借鉴交付边界，不能把其中的 Task
  直接等同于从任意聊天自动晋升的持久业务对象。

  编排策略，不是 Loom 单 owner、提交与验收状态机的替代品。
- [LangChain Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)：
  可以在选定工具动作前暂停并批准、编辑或拒绝；可借鉴权限边界，但 Loom 不引入
  该运行器、第二队列或所有工具统一审批。

判断：应分开语义建议、正式建 Task、领取已有 Task 三件事。当前
`claimMessageAsTaskTransaction` 将后两者原子合并；rationale 只要求非空，
所以它证明并发唯一性，不证明用户意图正确。Jev 也不能提供授权证明。
此前 Jev 实验测的是路由/检索，未验证 Task 意图分类；不得声称已证实它不擅长
该分类。当前不引入新的付费分类器或实验批次。

建议第一条完整业务链：频道讨论/直接工作 → 提出需追踪的交付事项 → 明确建
Task → 单 owner 领取 → Task Thread 协作 → 提交 → Human 验收。

明确建立/授权的 Task 不重复确认），还是频道显式开启实例自动创建。
自然语言里的“用户已经同意”不能由 Worker 自报作为授权。若选择前者，最小版
建议通过普通回复提出，Human 沿现有创建 Task 命令确认，不先造 proposal 状态机。
已有开放 Task 的原子领取继续保留，不要求逐次批准。

1. Kernel 为 Task 创建/消息转换建立同一个授权判定，覆盖单项、批量、转换及
   可被实例调用的认证门面；保留旧 Task 的执行、幂等、最新事实与单 owner 守卫。
2. 对齐 Worker 帮助与常驻协议，移除“只要写代码就必须 claim”；拒绝创建时给出
   可以继续普通回复/工作的说明，不把权限拒绝变成无休止 Activation 重试。
3. 使用已有 Task/Thread/事件链实现控制台最小创建、指派、查看、提交验收路径；
   不改冻结前端，不新增 Task 专属 session、嵌套任务编排或分类模型。
4. 先免费回归：普通消息即使模型硬调 claim 也遵守入口政策；已授权 Task 单 winner；
   所有创建门面一致；幂等重放；跨频道拒绝；仅频道现有实例参与；提交消息只一条；
   Run 结束不自动完成 Task；重启后 owner/Thread/状态保留。
5. 必要检查与真实控制台验收后，再申请一批有界真实 CLI 流程验收；分别统计任务
   交付与普通消息，不能重复 P89 只统计 message.posted 的漏计。
