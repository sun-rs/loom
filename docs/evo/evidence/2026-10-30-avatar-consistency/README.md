# 随机头像闪动与成员头像一致性

Owner 2026-10-30报告：随机按钮导致整个弹窗闪动；Role头像保存后消息正文、频道成员仍显示旧头像。本批修复这两个已复现缺陷，不迁移整版Web、不改变实例执行配置。

## 根因与修复

- 随机按钮每次读取`role.list`、禁用整个图库并插入状态行，导致变灰和高度变化。改为打开编辑器时读取一次占用集合，后续随机仅改变本地草稿；初次读取只禁用随机按钮。上传仍沿用原有权限及保存流程，准备状态使用无布局占用的读屏提示。
- 消息成员适配器、`readOnlySender`直接丢弃头像，频道成员又只读冻结Agent修订。新增纯展示投影：Instance ID→其稳定Role ID→该Role当前头像，缺失时回退保留头像；同名删除重建不混淆。Role保存成功后使共享只读身份投影失效，现有页面即时取得新头像。焦点恢复和既有周期读取覆盖其他窗口的更新。
- 消息正文、成员条／成员页、实例资料／列表、工作动态、搜索、收藏、消息列和文件评论接入这个投影或保留的成员头像。没有把上游Store变成业务真相，也没有改写历史消息、实例、Agent执行修订或原生session。搜索／收藏等附加入口为接线与类型覆盖，本批浏览器重点验收消息与频道成员，不宣称逐页视觉验收。
- 原官方源码、生成输出、图库和UI包版本均未修改。本批属于Loom身份数据接线维护。

## 验证与证据

[旧实现失败](red-browser.txt)：五次随机新增5次Role读取（累计6，相比初始1），与“点击后本地预览”的断言冲突。成员投影的新增测试同时复现原先`null`而非头像键。

[定向检查](checks.json)记录类型、构建、单元测试与格式。没有运行全后端、全前端浏览器或付费CLI实验。

- [Chromium](chromium/browser.json)、[Firefox](firefox/browser.json)、[WebKit](webkit/browser.json)：均在1440×1000和390×844测试；每个视口连续随机5次，零新增Role读取，图库节点保持启用，弹窗位置／高度不变。
- 保存头像后，消息正文、频道成员条与成员页均显示新图；桌面路径通过站内导航验证，无整页刷新。手机路径另含刷新后显示验证。
- 对比保存前后`agent.get.currentRevision`精确相等，以及`role.list.instances`除派生`isCurrent`之外精确相等。保存Role会自然使`isCurrent`变化，不把这一派生事实伪称为配置被改写。
- 隔离真实Core＋假CLI目录；预置Human消息后才创建实例，仅在浏览器时间线读取响应里投影消息作者用于展示验收。修正夹具之前曾在创建实例后发消息而触发假运行时错误；没有调用付费模型，也不把该调试尝试算作产品成功执行。
- 截图：每个引擎目录中的`picker-1440/390.png`和`channel-members-1440/390.png`。虚拟视口不等于实体PWA系统栏验收。

正式服务已在修复提交`b9854006`推送后，按[部署收据](deployment.json)完成完整备份校验、迁移预检和精确服务的平滑重启。schema91、14个保护表、通知／记忆文件和原TLS配置保持。LAN／Tailnet首页使用原CA验证，静态页匹配本批构建。

[正式Firefox页面](formal-page.json)在1440与390打开既有Role、各随机5次，零新增请求、弹窗几何稳定、图库保持启用；关闭上下文丢弃草稿，没有保存或创建测试对象，保护表校验值保持。正式环境未通过修改用户Role来重复保存流程；保存到消息／成员的回环已由上述隔离Core验证。

## 长期UI路线评估（建议，尚未更改已批准目标）

最低维护复杂度的主线应是一套完整、可重复构建的官方源码版本及其匹配依赖／CSS／资源，整体固定后只在明确的SDK、身份、路由和能力接口适配。官网变化进入候选清单，按批整体升级；不再逐位置抄样式、跨版本拼组件。

当前已取得的Web1.21.40完整可执行发布图与原始TSX／类型／构建工程是两种不同材料。完整发布图已经验证取得，整版Loom业务适配尚未验收；取得文件不能证明低成本的长期适配。若优先稳健，可选择已能完整构建的官方源码基线，并接受与官网新特性的版本差；若坚持1.21.40，则先完成整包适配可行性验证，不能回到“旧页面＋40片段”。本批没有擅自降级，也没有把原先1.21.40＋0.52.2的目标改成1.21.23。
