# 原 MCP 冷恢复：透明 wire 免费定位

只运行一批，真实安装 Codex 0.160.0 经生产 driver、正式 guard、私有字节镜像代理及 loopback 假服务；真实 Kernel/Worker 发布。三轮同一 instance/session，前两轮同 runtime，空闲正常重启临时 daemon 后换 runtime。无产品修改、无付费或正式状态操作。

| 阶段        | 假 HTTP / 记录生成 | MCP 内层完成 | raw outer 完成 | interrupt |
| ----------- | ------------------ | ------------ | -------------- | --------- |
| 初次        | 1 / 1              | 1            | 1              | 1         |
| warm        | 1 / 1              | 1            | 1              | 1         |
| cold resume | 2 / 2              | 1            | 0              | 0         |

初次和 warm 都先捕获完整 raw outer 输出，才捕获 turn/interrupt；warm 的 outer 输出还含 loom_reply 返回之后的 FAKE_OUTER_AFTER_REPLY，不能提前在内层完成就截断。冷连接全部已捕获通知中 rawResponseItem/completed 与 rawResponse/completed 均为零；仅有 MCP 内层完成、随后 FAKE_DONE agentMessage 和 turn/completed。这使现有要求外层完成的安全屏障持续等待，正常完整发表后仍发生第二次请求；不会据内层完成冒充外层结束。

真实 resume 请求确实携带 experimentalRawEvents:true，但安装版生成 ThreadResumeParams 未声明它；完整生成 schema 的 thread/settings/update、turn/settings/update 与初始化能力也无该开关。只有 thread/start 明确声明。没有查到可验证的正式同 session 恢复开启方法；任意 config 键/未公开实现仍不能凭 schema 排除。不能换 session 或猜参数规避这一连续性限制。

三次唯一消息、marker、Run 与实际消费 ACK 均完成；计量分别 100/20、100/20、200/40（仅夹具合成值），冷第二条没有漏计。交付与计量验证通过，冷单请求没有达到，不是总体效率验收。

捕获点位于正式 guard 上游；guard 的服务端消息源码原样转发，不能把 write 等同 driver 逐条消费确认。代理/同步日志有微小时序扰动。本批直接支持 raw 通知差异与现屏障不 interrupt 的一致路径，不能外推所有安装、真实随机模型或价格。原始 measure 没传 replyAt，其 before/after 生成划分不作时序证据。原始脚本 status=passed 仅为交付断言，不是效率结论。未再跑样本。

离线回放直接使用当前生产 createCodexFinalInterrupt，并明确采用反事实 arm 时点：每 turn 在 MCP 内层 completed 后立即 arm（并非声称观测到真实 Host arm 时间）。初次/warm 均到 raw outer 后才发 interrupt，cold 不发。证明所捕获的 outer 缺失足以触发现有保守路径，不证明唯一底层原因。

[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server#message-schema)说明生成的协议 schema 与运行该命令的 CLI 版本对应；本次依据安装版生成结果，不能把当前在线文档当成该版本实现证明。在线页面也未提供本次所需的恢复 raw 开关，未据此猜测配置。

保留现有保守回退，未改产品、未部署、未升级用户 CLI。缺失外层完成事件时不使用内层 MCP 成功、延时等待、文本标记或 transcript 替代执行结束证明；不替换 session、不修改其历史。本批定位成立不代表全部成本问题解决：P122 两臂生成数相同的长期输入差异仍独立存在。暂停围绕此边界重复探针，后续只有取得可验证的同 session 事件接口或上游修复后，才重新验收冷恢复提前停止。真实质量与长期累计成本沿用现有独立判据。

## 上游问题草稿（仅保存，未发送）

Codex app-server 0.160.0: how should a client enable rawResponseItem/completed after resuming the same thread in a fresh app-server process?

In an isolated local Responses fixture, thread/start with experimentalRawEvents:true emits raw custom_tool_call and custom_tool_call_output notifications. A second turn in the same process does too. After a graceful idle shutdown, thread/resume of the identical thread emits normal MCP item/completed notifications but no rawResponseItem/completed or rawResponse/completed. Complete code-mode outer output remains in native history and reaches the next model request. Adding experimentalRawEvents:true to resume does not enable notifications; the installed generated ThreadResumeParams does not declare that property.

We also checked ThreadSettingsUpdateParams, TurnSettingsUpdateParams and InitializeCapabilities in the complete experimental schema generated by this installation. We did not find a documented setter. Is there a supported way to resume the same continuous thread while retaining raw outer tool-result notifications, or a different documented completion event that proves the entire code-mode cell has finished after its inner MCP call?

A cell may execute additional operations after its MCP tool returns, so inner MCP completion alone is insufficient for safe interruption. We do not want to create a replacement thread or infer completion from provider prose. This is a local fake-model reproducer, not a claim about real-model quality. Raw private artifacts contain local identities and should not be attached without sanitization.
