## 失败原因与证据边界

1. **免费预检/启动器问题。** 安装的 Kimi 从 2.1.1 变成 2.3.3，审计版本门禁拒绝继续；不把升级原因臆定为已证实。独立取得 npm 2.1.1，主程序 SHA256 与已审计版本完全相同，设官方 `KIMI_CODE_NO_AUTO_UPDATE=1`，不降级全局 CLI。Herdr 交互 shell 会影响环境继承，测试面板改为显式导出隔离 HOME/effort/PATH，并核实界面显示 2.1.1 / low。文件夹信任提示、纯文本/空结果返回也在免费预检处理。
2. **第一对是启动器失败，非产品失败。** Loom 初始说明已结束，但 runner 用了错误终态名；Herdr 初始回复很快，runner 没捕获短暂 working 状态而持续等待。两者均由本次执行代理发送 SIGTERM 停止；旧日志中的 `Owner interrupted` 是不准确的统一错误文案，不表示用户中止。样本不替换。针对实际 exited/exit_code + Activation 完成的条件补了失败后通过的检查；原生改为实际新 receipt + idle，而不是依赖瞬时状态。
3. **第二对 Loom：旧句柄误用。** 最新 wake 明确携带新 `--turn` 及 native-final 选择；Codex 仍尝试用上一轮句柄经 Worker 发评审请求，得到 `TURN_HANDLE_INACTIVE`，又在无句柄检查时得到 `TURN_HANDLE_REQUIRED`。最终文本承认评审未完成，没有向评审者发起新的明确 @ 请求。无待执行调度，并非消息已经投递但 B 未被唤醒。现有证据支持调用/恢复失败，不支持把旧句柄放宽为有效。
4. **第三对 Loom：未收尾工具 + 恢复草稿。** 设计评审普通回复不带重复 @，Kernel 自动交回成功。实现回合留下 `rg --files ...` 的 `tool_start` 而无 `tool_end`；Host 报 `warm turn left tools in flight; runtime stopped`，下一次恢复的最终输出 held（based-on 19，已见位置27；此前 Worker 消息已发布），Activation quarantine，runner停止。此前手动 Worker 发布的“请审阅”也没有新的 @，不能自动推断接收人。外部检查通过不覆盖这些交接问题。

归一化持久工具轨迹离线重放确认恰有上述一个未闭合工具；这是轨迹核对，不是完整原始 app-server 重放。第三项不是漏给新句柄；第四项不是目前已经证实的计数误报。轨迹里的未闭合命令已定位；相同命令在本轮终端立即返回，原因仍需在相同 Codex 工具环境里做定向复现。不得删除执行隔离、旧句柄校验、明确寻址或草稿因果围栏来让实验过关。不得仅凭这两次模型行为开始全局 prompt 重构。
