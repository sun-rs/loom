# Schema 修复后固定对照及因果参数说明修复

Owner 在修复汇报后要求继续；本批针对 Codex / gpt-6-luna / low 与 Kimi / k3-256k / low，计划各三对、每臂三轮，交替顺序，沿用原固定快照、问题、正常历史与自动记忆禁用政策。源版本为 `29145cda`。每 CLI 观察上限 200 万输入、3 万输出、40 分钟；执行或计量失败即停止，不补跑。

## 实际结果

两家都在第一对触发停止条件，故没有形成重复样本的新验收结论。

| CLI   | 原生输入 / 输出 | Loom 输入 / 输出     | 结论                                       |
| ----- | --------------- | -------------------- | ------------------------------------------ |
| Codex | 52,835 / 884    | 191,348 / 2,103      | 单对描述性输入比 3.622；不是通过或总体估计 |
| Kimi  | 92,004 / 1,202  | 已知 130,315 / 2,156 | 三个请求缺 usage，不计算完整倍率           |

- Codex 正常完成三轮回复，但首轮出现四次 `final_delivery_unconfirmed`，本次没有漏传 final。首次任务 9 次模型请求，后两轮各 1 次；原生为 2/1/1。模型还尝试 CLI 发表且漏 turn，触发既有 `turnHandleMissing:r1` 围栏，整批 failed。不能把失败样本删除后补够三组。原生累计 token 账本与两臂统计逐项一致。
- 新工具 schema 要求 final 后，模型本次所有 MCP 回复都带 final。新暴露的问题是：投递文本使用 CLI `--based-on-room-seq`，工具字段是 `basedOnRoomSeq`，说明未明确映射。重复拒绝后传入 4 才成功；后两轮正确传入 13、22，一次成功。这是可定位的接口说明缺口，不是应删除因果围栏的证据。
- Kimi 三轮 Run 全部成功退出，没有旧 EOF 超时；但每轮工具回复后仍有一个后续请求被取消、缺终态 usage。原生 wire 中 8 请求仅 5 份 usage，已知合计与产品账本一致；原生对照 4 请求/4 usage 完整。已完成工作不等于用量完整。15 秒等待只修复正常退出误报，不解决取消造成的计量缺口。

## 后续最小修复

所有 CLI 共用的 MCP 参数说明及每轮提示明确：将 Reply context 的 `--based-on-room-seq` 值填到 `basedOnRoomSeq`；不猜测、不取更新消息的序号，投递不完整先 message-check。不自动填序号、不默认 final、不改 Kernel ACK/幂等/因果规则。已有草稿修订保持原上下文。

增加缺映射的失败测试后修正；12 项共用 schema、提示、stdio、实际 application-service 拒绝/接受围栏测试通过，类型检查通过。测试文件在 Kimi 运行末期添加，运行时代码在整个付费批退出后才修改；因此本批不包含新参数说明的效果。没有修改后再自动付费补跑。
