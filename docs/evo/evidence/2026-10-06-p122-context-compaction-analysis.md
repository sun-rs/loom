## 可以确认的体积

逐份读取 JSONL 中 `response_item/custom_tool_call_output` 的两个 `input_text`：第一个为执行宿主提示，第二个为 MCP JSON envelope；解析第二个的 `content[0].text` 得到成功回执。按 UTF-8 编码计数，并断言全部 36 份均为 `published`、`isError=false`、空 `activationIds` 和同一组九个回执字段。

| 可见文本                   | 每份字节 | 36 份合计字节 | 含义                                   |
| -------------------------- | -------: | ------------: | -------------------------------------- |
| 成功回执 JSON              |  316–317 |         11402 | 含身份、目标、序号、消息引用及去重结果 |
| MCP envelope               |  399–400 |         14390 | 已包含上行回执，不能重复相加           |
| 执行宿主提示               |       47 |          1692 | 与 envelope 并列的工具输出文本         |
| 候选删除空 `activationIds` |       19 |           684 | 仅内层 JSON 的理论差值，未应用         |

因此，可见工具输出合计 16082 字节，其中 envelope 包装与宿主提示合计 4680 字节。它们的所有权不同：Loom 控制 MCP 回执投影，原生 CLI 执行宿主控制工具输出呈现，不能通过改 Loom 回执假定全部包装都会消失。

这些是新增历史文本的字节量，不是 tokenizer 结果、完整 provider 请求、重复计费总量或价格。后续请求会携带历史，且存在缓存；不能用字节比例推算省下多少 token，也不能将整个回执体积视为可删除空间。

## 对收口的意义

P122 两臂每阶段都只有一次已报告生成，因此“确保一次用对工具”在这个样本已经做到，仍不足以消除持续累积的输入差。当前每人相邻轮增长差 487–506 token 不能全部归因于以上可见文本，也不能由 16 或 19 字节删减证明解决。

现有证据支持暂停零碎文案优化。若继续做传输优化，应先免费捕获最终实际请求并区分：首次常驻说明、当轮投递、工具调用/回执、CLI 自带历史和实际同伴内容；分别统计新增内容与后续历史重放，保持原生对照记忆关闭、同 session 连续且历史不改写。已有可见历史测量不能冒充完整请求归因。先以隔离 loopback 假 provider 验证捕获与分账，无需付费模型；捕获不到的字段明确 unknown。

只有识别出可观且由 Loom 控制的重复项，才进入新契约比较、TDD 和生产修复。真实效率仍需新的、单独授权的同质量长期配对；免费测量不能证明模型质量或账单收益。对 `0700/0744` 错误不加题目专用提示，也不靠删掉失败阶段、替换原生分母或补跑挑选成功结果收口。

本轮仅新增分析文档和测量数据，能力状态、部署与付费台账均不变。
