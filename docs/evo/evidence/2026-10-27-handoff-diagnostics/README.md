- Codex 21次生成中有7次 loom_reply 调用：3次新回复遗漏 final，被入口参数校验拒绝；补齐后成功，另一次收尾直接成功。最终4条规范频道消息，没有把参数拒绝当成已发表，也没有因此产生重复消息。

## 源码对应

`packages/protocol/src/worker-mcp.ts` 的公开 inputSchema.required 仅有 body，final属性说明明确要求新回复必须传入；真正校验由Zod superRefine执行，因为修改 held draft 又必须省略 final 和 basedOnRoomSeq。

`packages/agent-host/src/worker-mcp-entry.ts` 对不同参数问题只返回统一的 Invalid loom_reply arguments，未说明缺失final。这使失败后的修正信息不充分。公开结构约束比服务器宽松是已确认事实，但模型已经收到字段文字说明，不能断言这是所有遗漏的唯一原因。

不能直接把final设成默认值来省请求：true可能过早结束，false可能遗留执行；也不能把final全局设为必填，破坏修订草稿的已有合同。若引入条件schema，需要单独核对多家CLI的schema接受能力，不能用仅一家的表现推断。

## 结论与最小后续

上一批完整业务交付通过仍成立，但严格的指令遵循和通信首试成功并未全部通过。这是对既有验收范围的补充，不是悄悄把失败计入成功。

下一项最小维护应改善共用MCP参数错误：明确缺失/冲突字段以及新回复与草稿修订的合法形态，保留身份、freshness和显式final围栏，先用假CLI/协议测试证明非法调用不转发、合法调用不变。不要先改系统prompt、增加业务编排或开放Codex native-final。错误原生等待先记录为模型工具选择失误，不能因此全局禁止用户允许的原生子代理。

没有原生/Herdr对照，也没有反事实重放；不把某次请求全部输入算成可省token，不声称能降低某个百分比，不把单一Codex样本推广到其他CLI。当前只找到明确可改进的参数诊断，未发现需要重构Room/Session架构的证据。
