# 同样目标为何多消耗：长期输入、缓存与模型可见协议分账

**当前证据指向协议表示负担，而不是 P122 中模型多执行了很多轮。业务问题之外，Loom 让模型携带更多常驻规则、路由信息和工具交互历史；缓存差异进一步扩大未缓存输入倍率。此前将所有成功回执字段视为必须进入模型的安全要求，判断过度保守，本报告予以纠正。**

本次只分析已保存的真实 P122 轨迹和另一批免费完整请求，没有新增 provider 测试调用或 CLI／服务运行，没有修改产品或原生历史。分析身份为 `9cac288` 之后的文档工作树。两个数据集分别回答实际消耗和请求组成，不能把免费字节比例套成 P122 的 token 或账单归因。

## 实际消耗：同样生成次数，输入差持续增长

[P122 原始裁决](2026-10-06-business-long-p122.md)保持：两臂各三个连续 session，每人十二阶段；原生 36/36 正确，产品 33/36，质量与效率未验收。重新核对六份完整轨迹，72 阶段各有一条已报告生成，用量逐项匹配。[逐阶段算术与轨迹 SHA](2026-10-06-long-cost-attribution-tokens.json)保留所有错误及后续成本。

| 观测量           |   原生 |   Loom |   差额 |
| ---------------- | -----: | -----: | -----: |
| 已报告生成       |     36 |     36 |      0 |
| 总输入 token     | 532998 | 732101 | 199103 |
| 缓存输入 token   | 474624 | 636672 | 162048 |
| 未缓存输入 token |  58374 |  95429 |  37055 |
| 输出 token       |    459 |   1755 |   1296 |

三人的首轮输入差为 3011、2808、2617 token，末轮已增至 8428、8281、8014。相邻阶段的差额通常再增加 487–506 token。不是只在开场多读一次说明，随后便不再承担代价。

可复算恒等式：以各人首轮观察差作为每次请求的基准，`199103 = 12 × (3011+2808+2617) + 97871`。基准重复项占 50.844%，高于基准的累计增长项占 49.156%。**这是算术分解，不是识别出精确的固定协议 token**；首轮包含初始投递、成员事件等差异，后续也含实际答案差异。不能把两项直接当作某个提示或工具的因果计费。

固定内容的相对占比可以随业务历史增加而下降，但它不是启动后消失的一次性费用；每轮额外留下的历史还会继续增长。没有证据支持期待总体倍率自然回落到 1。

直观上，即便没有再调用一次读文件工具，下一次模型请求仍会携带正常会话历史。若以本样本约 500 token 的相邻输入差增长作简化示意，十二轮中早先增量反复出现的累计量约为每人 `500 × (11+10+…+1) = 33000` token。这解释了“没有多做一次业务操作，累计输入仍会明显增加”的机制，不是把每个新增 token 都判成可删协议，也不是对其他任务的预测。

## 1.63 倍还包含缓存影响，但不只是首轮问题

总输入倍率为 1.373553，未缓存输入倍率为 1.634786。原生整体缓存占比为 89.048%，产品为 86.965%。代数上：

`未缓存倍率 = 总输入倍率 × 产品未缓存占比 / 原生未缓存占比`

`1.634786 = 1.373553 × 1.190188`

首轮额外未缓存输入为 20468，占全部额外未缓存输入的 55.237%。其中原生 B 首轮已有 12032 缓存输入，产品 B 为 0；该轮总输入仅差 2808，未缓存输入却差 14840。没有服务端证据解释缓存命中原因，不能将它定性为 Loom 缓存失效，也不能从成本账中扣除。

后续 33 阶段仍有实质差距：总输入为 493527 对 684194（1.386 倍），未缓存输入为 30935 对 47522（1.536 倍）。这只是解释性分窗，**完整样本的主结果仍包括首轮**，不能用续轮子集替代全量裁决。

输出也不是业务答案变长四倍：每阶段已报告输出恰多 36 token，合计 1296。原生输出普通答案，产品生成 `exec`、`loom_reply`、参数和打印回执的代码。该语法差在轨迹中可见，但没有逐片段 tokenizer 证据将 36 token 再分配。两侧已报告 reasoning output 均为 0，不据此断言服务端不存在隐藏计算。

P122 本身也重新核对过公平条件：六个 session 都只在首轮新增一份完整源码；后续未重发，两侧题序相同、官方自动记忆关闭。不是原生漏材料，而是平台表示与实际历史不同。模型随机性仍影响质量和路径；本报告没有用它解释已能直接观测的协议负担。

## 修正此前判断：内部完整证据不等于模型必须看完整证据

此前压缩审查只允许不改变既有回执形状及全部常驻语义的局部文字压缩，所得收益很小。不能据此推导结构性减负也没有空间。

- `protocol/worker-mcp-receipt.ts` 的 `workerMcpPublishedReceipt` 是完整 Worker 响应校验后的模型输出投影。
- `agent-host/worker-mcp-execution.ts` 仍须完整读取、验证响应，维持幂等与未知结果围栏；这不要求输出投影保留所有后台 ID。
- `kernel/run-attempt-final-reply.ts` 按真实 consumer 状态检查 ACK 和提交资格；`agent-host/runtime-final-reply.ts` 读取 Kernel final marker。它们不靠模型看到或复述作者、事件等 ID 判断完成。
- `agent-host/codex-outer-output.js` 检查原生工具执行的完整外层结束证据，不解析成功回执中这些业务 ID。
- 旧实验 `multi-channel-mcp-validation.mjs` 的完整回执深等值是现有接口断言；改变投影时应重新验证模型投影与完整持久证据的关联，而不是把旧形状本身当成安全不变量。

因此，完整事务和审计链必须保留，模型可见成功回执则可以单独设计。普通成功与 held、拒绝、未知结果不可混淆；引用、未解析 mention、草稿替换等会影响下一步的内容仍需逐场景验证。不能一律改成一个 `OK`。

常驻 CLI 文档同样不是目标合同要求的固定排版。当前稳定规则、每轮指引与工具 description 对回复路径有重叠；当前使用的是 MCP，仍常驻另一条 CLI 回复路径的细节。必须保留能力可发现性、final 行为含义、上下文确认及安全恢复，但不等于所有操作语法都必须提前进入每个普通对话。把说明改为按需提供会不会反而增加 help 和恢复调用，需要验证，不能直接假定有净收益。

## 值得实施前验证的改变与量级

以下为已归档输入上的离线表示反事实，**没有真的修改或重放到 CLI**，不改变历史。数值不是已证明可安全删除的成本，也不能相加作为 token 节省承诺。

1. **缩小普通成功回执投影。** 对本夹具全部普通、未去重、无警告成功，保留 `published + messageId + roomSeq`，其余 MCP/执行宿主包装和调用 ID 不变，历史结果累计少 54846 字节，占额外 input 的 7.29%。这条改变不依赖修改原生工具协议；但异常、幂等重放、后续引用和消费者兼容仍需 TDD。它只解决一部分，不能单独称为成本达标。
2. **精简模型可读的规范投递。** 24 位实例名后缀的交叉份额为 45000 字节；成员创建内部字段的当前呈现累计 25020 字节。短名必须仍唯一、可正确用于下一次 @，不能只是美化后让模型误路由；不能改写旧实例的历史身份或删除投递/ACK 覆盖范围。精简原始运维字段投影与删除事件不是一回事。
3. **减少普通回复常驻的双路径说明。** Worker CLI/Task 段累计 99432 字节，Message Notifications 段 51840 字节。这是待逐语义审查的体积，不是全部可删。保留最小共同入口与按需回退，避免再维护多套场景提示；已有 session 的原始常驻说明不一定可原位替换，收益与兼容必须分别报告。
4. **原生工具与正常结束能力列为受限候选。** 通用 MCP 包装累计 122076 字节，但 CLI 决定其注入；已有原生工具研究尚未解决存量工具更新等边界。中断提示累计 69696 字节，但中断本来用于避免一次额外生成，直接取消它可能更贵。冷恢复限制另见[已定位证据](2026-10-06-mcp-product-cold-wire-free.md)，它不能解释 P122 生成数相同的全部差距。

本轮结论是：**确实存在可重新设计的模型可见协议负担；不是所有多出来的内容都是协作的必要成本。** 优先评估 Loom 自己控制的成功回执和投递/说明投影，不再把所有字段冻结为不可更改，也不把模型一次正确调用当效率达标。安全、质量、完整计量分别验证；存量会话不轮换、不修改历史，新数据不覆盖旧失败。没有新的付费验收或收益承诺。
