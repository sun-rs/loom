# P113：12阶段连续任务的累计成本

最终输出试验路径与原生 Codex 各完成同一 session 的12阶段审查，两者均20次已完成生成。全部启动和业务成本计入后，试验路径总输入为原生的 **1.101倍**，后六阶段为 **1.067倍**；未缓存输入却仍为 **1.711倍**。这支持“不能用首轮倍率代替连续任务累计倍率”，但不证明实际账单仅增加10%，也不代表正式默认路径已经可靠。

默认路径在第一阶段发生“已经发表 final、没有确认 delivery、同 Activation 重试再发表”，本臂失败停止。整批机器状态为 `partial-failure`，不能把完成的试验臂改称整批通过。两份完整答卷独立盲审均65/72，但均未全面遵守字数要求；技术质量、指令遵守、传输、成本分别判定。

## 默认路径失败的因果链

1. 模型先把CLI的target/turn身份字段传给MCP，schema拒绝；修正时把合法的 `basedOnRoomSeq:4` 一并删除，仅保留body和final。
2. MCP成功发表seq9并返回published回执，final marker触发中断。但没有模型显式序号，Kernel正确地不伪造delivery ACK。
3. 同一Activation因 `activation delivery is not acknowledged through sequence 4` 被判可恢复并重试；不是第二条Human消息，也不是新Activation。
4. 第二Run重读文件，带旧seq4的回复又被自己的seq9触发hold，之后check、两次help、send-draft，发表第二份seq17，才完成ACK。

首Run3次生成，第二Run6次；全部已报告成本已恢复核账。数据库实际有两个工具final marker，门禁 `finalMissing` 名称在这里表示“不是恰好一个final”，不能误读成零marker。`duplicateReply`准确。

这既包含模型工具误用，也暴露平台组合行为：允许缺显式消费序号的final先发表并中断，再为缺ACK重跑已答义务。不是MCP传输必然昂贵，也没有证据证明同一幂等调用被重复写入。下一刀应先用免费回归固定这条因果链，明确final提交前的消费证据要求及已发表后的恢复行为，保留ACK与未知写入围栏；不能靠补假ACK、删安全校验或继续微调提示掩盖问题。本批未实施该修复。
