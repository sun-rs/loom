# P119：默认 MCP 首轮误填 threadId，重试后送达，长期对照停止

**原生三 session 各十二轮全部通过；产品首轮答对并送达，但第一次 MCP 调用把频道名填进 threadId，被拒绝后重试。实际两次调用、两次生成，不满足冻结的单次调用条件，按首错停止，未建立长期成本倍率。** 本批不补跑、不改变判定条件。

## 冻结与观察

owner“我同意”批准[默认 MCP 方案](../multi-channel-mcp-inline-plan.zh-CN.md)的一次 native→worker-mcp 配对。干净源码 `f87f0d3c8ac909c41a17c0f72287a57fc44e1f8e`，实验身份 `25c57119ac664b208e06f270cf76b4a1119fe82dd8bf00cff7f7236a792527f3`。Codex 0.160.0、gpt-6-luna/low，双方官方记忆关闭；final-output 两开关关闭。每臂三实例×十二轮，采用冻结的输入与时间准入软上限，未触及上限。

原生 36 阶段全部通过：三个独立连续 session，完整材料各首轮一次、后续不重发，零工具，答案逐字正确，36 次已报告生成。

产品只运行 A 首轮，实际轨迹如下：

1. 调用 `loom_reply`，正确 body、final=true、basedOnRoomSeq=8，但填写 `threadId:"#multi-efficiency"`。
2. 工具返回 forbidden：`Thread is outside this Worker execution scope`，没有发表。
3. 第二次调用省略 threadId，其他业务参数不变，返回 published。
4. SQLite 与原始回执对应一条消息、一个 Run、一个 completed Activation、真实消费者 ACK、ordinary final marker；Host 收尾中断，回复后没有额外生成。

检查器随后以 `expected one MCP tool call: 2 !== 1` 停止本批。失败是单次调用条件不满足，不是 MCP 连接故障、重复发表或没有回答；也不是检查器拒绝所有两次生成（唯一调用后的跟随生成本来允许并计费）。产品 B/C 和后续阶段没有启动。

## 接口诊断与后续边界

当前工具定义 [worker-mcp.ts](../../../packages/protocol/src/worker-mcp.ts) 声称回复 delivered conversation，却暴露一个没有 description 的可选 threadId 字符串。当前调用链省略该参数即可正确定位。实测证明本次模型误用了参数，并在省略后成功；“参数歧义促成误用”是有源码支持的推断，不能从单样本证明唯一原因。

建议先免费设计和验证更窄的当前目标回复 facade：由运行时绑定已投递目标，保持 Kernel 权限、因果栅栏、线程隔离和 held draft 语义；显式其他目标仍走已有路径。不要通过把频道名容错转换为 thread ID、吞掉失败调用成本或重判 P119 来制造通过。改变工具契约需要独立设计及 TDD，本批没有实施产品修改。
