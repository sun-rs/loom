### 实际额外调用

- 第1轮：两次把Worker命令误写为 `cat` 调用；其间有效调用help；之后有效但多余的message-read；再读业务源码并post。误用产生的查帮助与读取增加生成，业务文件读取量没有增加。
- 第2轮：先用正确当前turn执行读取；第一次post把当前标识抄错一个字符，得到 `TURN_HANDLE_INACTIVE`；第二次删掉turn，得到 `TURN_HANDLE_REQUIRED`；第三次恢复准确参数成功。不是旧session、过期唤醒元数据或平台拒绝正确参数。
- 第3轮：读取Worker消息后post，两次生成对原生一次。不是额外Run。

`turnHandleMissing:r2` 检查所有post尝试，因此保留第二次被拒绝的无turn调用作为失败；**最终成功消息带有正确turn**，不能把该门禁错误写成执行围栏失效或成功帖子缺参数。即使只看成功帖子，原始失败调用及费用也不能从测量中删除。所有轮次的效率超标结论独立成立。

## 免费后续研究：从命令拼装转向显式原生工具

本节是P97结束后的免费研究，不是新的付费验收或已部署能力。产品未改、session未替换、目标合同未改。

### 可消除的负担与不可夸大的算账

P97并无“原生一次回答，Loom必然两次生成”的硬下限：三轮成功post都显式final并终止。若模型直接走业务路径，首轮读文件＋发布、续轮各发布，候选链为2／1／1，与原生相同。删除两次cat误用、三次多余read和两次失败post但保留首次help时，候选链是3／1／1；仅修参数错误仍不足以使首轮回复前生成数达标。

这些是执行路径分析，不是优化后实测。历史输入逐项剪裁不能预测新调用的缓存、后续上下文、质量或延迟，因此不发布“必然降至某个倍率”的承诺。本次首请求差较小，而额外协议生成反复携带完整上下文；继续只压短说明文字或修单个调度漏洞，没有证据能收口。

### 选择的最小候选

先研究**一个Codex内部原生发布工具**，仍调用现有Worker应用服务。模型提供正文、明确的final／非final意图以及现有业务新鲜度／目标参数；身份和运行凭据由可信原生回调绑定，不放进模型参数。首刀不自动填Room最新序号，不自动ACK，不将普通assistant final/stdout变为消息；语义复用现有post，避免先改合同。

目前的22字符随机turn标识是在暖进程跨轮复用时，阻止旧shell借到下一轮权限的设计。不能删除围栏、改为查“最新active turn”或让旧入口重定向到新凭据。新工具应由AgentHost把native thread／turn及runtime generation固定映射到原Run和原凭据；所有业务状态与幂等仍归Kernel。工具参数中的actor、credential或Run字段一律不接受。未绑定身份、已结束／撤销／旧generation的调用在进入应用服务前拒绝。原生帧只是调用身份来源，不是任务完成证据。

这是Loom自己的Room Worker通信入口，不恢复已退役的第三方MCP管理，也不建设通用工具平台。CLI保留为兼容路径，但不通过“再给一个更长命令模板”宣称结构性解决抄写风险。进度发布仍须可用，不能重新引入普通消息默认final。

本机Codex CLI 0.160.0生成协议显示：`thread/start`有`dynamicTools`，`item/tool/call`的threadId／turnId／callId由协议提供，不属于模型arguments；`turn/start`没有可任意重设shell环境的字段。当前Loom两个Codex driver尚未接线此工具回调，未知请求走现有拒绝路径。

- 有效动态回复工具注册成功，新thread的turns为空；故意把dynamicTools设为错误类型时被协议拒绝。
- ephemeral thread读取完整turn被拒；另一个新建空持久thread的read/resume均返回 `list_turns is not supported yet`。
- 生成协议的resume参数没有dynamicTools。**因此只证明新线程接受注册，没有证明存量连续session追加工具、冷恢复后的工具保留或真正模型回调。** 空线程失败也不足以断言已有正常session不能恢复。

### 进入产品前的有限验证与停止条件

下一步只应做一个可丢弃的Codex小原型及免费验证，不同时改四家driver、memory、Task、UI或调度：

## 补充：代码模式与最终结果边界（2026-10-04）

后续免费对照已打通 `functions.exec` 内部的原生回复调用及同 session 冷恢复，且按每轮唯一返回标记核对了外层 `custom_tool_call_output`。此前超时不能归咎于动态工具：不注册任何动态工具、只执行 `text(...)` 也复现。延长等待后约30秒返回 `timed out negotiating with the code-mode host`；假模型随后结束回合，证明仅以 turn completed 判成功会产生假阳性。

精确子进程采样确认 Homebrew 的代码执行宿主已派生，但停在 `_dyld_start`，约112KiB footprint、无已加载映像。现有 daemon 安装副本的主程序及宿主与 Homebrew 均为同版本同 SHA256；独立启动该已有副本后，首次与冷恢复的代码模式原生工具调用均通过。没有连接既有 daemon/session，没有改 PATH、个人配置、二进制、签名或 quarantine 属性。此对照定位到安装路径／macOS 启动条件差异，尚不能只凭隔离属性差异断言唯一根因，也不能用它解释 P97 历史成本。所有模型回合仍只访问 loopback 假服务，官方自动记忆关闭。

最终回复时序另做四组免费原生协议对照，以 callback 模拟 Host 收到 final 提交信号，并故意延迟工具返回：

| 对照                      | 观察                                                                               |
| ------------------------- | ---------------------------------------------------------------------------------- |
| 现有 controller           | 工具返回前中断，外层输出为 aborted，唯一返回标记丢失                               |
| 只补 dynamicToolCall 跟踪 | 内部工具已成功，外层代码单元仍被中断；即使 preemptedFollowUp=true 也不能算完整交付 |
| 等对应外层结果再中断      | 外层输出先含完整唯一标记，再中断；本样本仅1次假模型请求                            |
| 不中断正对照              | 第2次假模型请求含外层唯一标记，验证夹具确实能继续执行                              |

所以不能把“给工具集合加一个类型”作为产品修复交付。已有 raw 事件可提供外层 call/output 的配对边界，但内部回调没有 parent outer ID；当前仅证明单 outer／单 inner 路径。多代码单元、并发调用、yield 后继续运行和事件缺失必须保守处理，不得把未知结果当作已闭合，也不得从诊断文本推导业务完成。

下一刀只做新建 Codex 实例的一个内部 `loom_reply` 闭环，复用 Worker post／revision，不新增 Kernel 队列或业务处理，不替换已有 session，不推广全量工具：

1. AgentHost 保留原 Run credential；driver 只传可信 thread／turn／call 身份。启动响应前暂存的请求须等身份匹配，旧 turn、旧 generation、未知身份均拒绝，绝不寻找最新凭据。

3. final 的 Kernel 提交信号与工具结果闭合分开验证。至少保住完整外层结果；并发／yield／缺失通知下不能为了省生成提前中断。不能只靠中断返回成功或 preemptedFollowUp 指标验收。
