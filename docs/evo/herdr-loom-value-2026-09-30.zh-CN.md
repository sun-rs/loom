# Herdr 与 Loom：双 Codex 探索性价值对照

## 结论

本次不能证明 Loom 比 Herdr 更省心或更经济。两边最终结论可用，原 session 续聊正常；Loom 的自动接力未按 A 初审 → B 反驳 → A 修订完成，出现轮内主动轮询、等待消息、提前修订及恢复后非目标成员作答。应先收口这条实际业务路径，不以更多付费措辞对照代替它。

这是单次探索性验收，不是 §6 正式效率门禁，不更改预算，不外推全部模型。Herdr 组也有质量问题：B 最初没有读代码，要求实际核对后才补读；补做的费用全部保留。

## 条件与范围

- 用户批准本批使用多个 Codex，Claude 不可用；只用批准组合 `gpt-6-luna / low`，原生 turn_context 逐轮核对，Loom Placement 也核对。CLI 0.158.0，产品 HEAD `8be0c77`，开始时工作树干净。
- 两组同一固定代码快照：`packages/daemon/src/state-backup.ts` 与 `packages/daemon/test/state-backup-runtime-credentials.test.ts`，共 684 行。快照哈希见证据。
- 只读审查临时凭据排除、provider session 文件保留、恢复证据边界。初审、反驳、修订、追加目录布局约束。测试实例未获代码修改、记忆写入或任务创建许可。
- Herdr：新建两个无焦点窗格运行原生 `codex exec/resume`；沿用效率门禁的启动隔离与用量采集。协调者把完整回答原样传给另一 session，没有摘要改写。测试结束后关闭本次创建的两窗格，未动用户已有窗格。
- Loom：正式 4176 创建专用测试频道及两个 Codex Role 实例；只发开场，让实例通过 @ 接力，随后进行恢复追问。原生组的进程每轮退出；Loom 初始使用热进程。
- 仅统计测试执行实例。**本次协调助手的 token/费用没有可取的完整计量，未计入；人工注意力时间也没有测量。** 不据此宣称全任务总费用或人工时间更低。
- 只比较同厂商、low 档和只读审查，不证明跨厂商互补、强模型组合或并发代码修改质量。

## 已确认的过程问题

1. **测试编排错误，非产品故障。** 第一频道的 Human 开场在接力说明里同时 @ 了 A、B，因此按产品合同同时唤醒两人；B 还把对 A 的初审要求当成本轮要求。该组留存为无效样本并单计费用；只急停此频道，没有删除其记录。第二频道只 @ A，其他 handle 不带 @，此后只唤醒 A 初审。
2. **Loom 的轮次结束仍依赖模型选择。** 正确开场中 A 首次发帖没带 `--final`，随后反复 `message-check/message-read` 等 B，同一 Run 生成 16 次。A 首次请求输入 10,868，原生 A 为 8,808（差 2,060）；本样本的大头是重复生成累计，而非首请求固定指令暴涨。A 又发等待消息并尝试错误的 thread 目标，守卫拒绝错误目标后它改回频道。
3. **额外发言与 freshness 相互放大。** B 发帖遇到 held 后重新读取/修改，共生成 7 次。A 的“最终修订”在 B 的成功发帖之前落库，B 随后也直接给最终修订而未按计划 @ A。账本正常完成两个 Activation，但用户要求的反驳接力没有成立。不是新建 session，也不是重复领取同一 Activation。
4. **SOS 恢复唤醒范围宽。** `room.sos.resume` 对全频道启用实例派发 manual attention（`packages/kernel/src/room-agent-sos-service.ts`），所以 B 也运行。guidance 明确只有 A 回答、B 无需回复，且原生输入确实含该指引；B 仍回复，A 又遇新鲜度拦截。属于现有恢复语义和模型行为交互；不能称普通 Human @ 定向规则被绕过。
5. **Herdr 的独立审查需验证。** B 初次只有一轮生成、没有工具调用，却说核对过代码；后续明确要求实际读取后才出现读码工具。A/B 相互同意不能单独证明质量。协调者补了一次质量干预、一次结果转交，消耗已计入。

两组最终都撤回“session 可能放在 turns 中”的假设，并区分文件保留与真实 CLI 恢复。未发现有充分证据的新备份漏洞。Loom 初审关于特权身份的风险表述价值低；Herdr 的反驳也曾重复前人推测。不能因参与人数而认定审查质量提升。

## 续聊和安全结束

- Herdr A 三次后续执行均复用原 session；B 补读也复用原 session。
- Loom 两个初始 Run 在 18:11:44/49 UTC 已退出完成，急停请求 18:11:58 UTC 才到达；并非人为中断使其产生不完整成本。随后仅对测试 A 的 idle runtime 核对 participant、PID、命令及无活动 Run 后发 SIGTERM。未重启 daemon，未动其他实例。
- 恢复后新 runtime 仍绑定 A 原 session `01a0ee5c-9f73-7050-8250-9a07ff7e922e`，并正确回应新增目录约束。B 继续原 session。证明空闲运行时重建的连续性，不证明执行中故障或 daemon 重启的所有路径。
- 最终测试频道空闲，四个 Run 均终止，全部 Activation 完成；无新增消息后的定时复核仍无新 Run。固定快照和源文件哈希未变化。
- 本次未改产品代码、未提交/推送、未重启正式服务。两项备份边界免费测试通过；文档格式和 diff 检查另行记录。未进行浏览器验收。

## 下一步建议

暂停扩大测试样本与 phase-4 范围。先对本次“发完后轮询等待”的轨迹做最小设计：如何在显式完成本次答复后可靠释放执行轮，把后续接力交回已有事件调度；同时保留合理的中途进度发帖，不把所有 post 都强制视为 final。保持 ACK、Task 和 freshness 围栏，不以调高预算掩盖问题。

可以保留 Loom 的持续记录、同 session 恢复价值；本次没有证明自动协作能降低介入成本。后续是否继续投入仍需这条业务链闭合后的真实任务结果，而不是 provider 数量。
