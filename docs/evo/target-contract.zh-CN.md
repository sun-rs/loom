# Loom evo 目标合同

日期：2026-09-24。来源：owner 2026-09-22 架构提案、之后 grill 的确认决定、2026-09-23 效率门禁结论。
本页是 evo 后端的唯一目标合同；evo 现状见 [status](status.zh-CN.md)。owner 于 2026-09-24 确认；标注"待定"的条目仍需 owner 决定。

## 1. 为什么重构

一个人格 Agent 背后一条 session 承接所有频道，会导致：跨频道串行阻塞；无关频道的上下文互相挤占，更早触发压缩；每轮调度开销大（约为原生 CLI 的 5 倍）。
目标：**用户能组建可复用的角色团队；每个频道里的每个实例拥有独立、连续、干净的原生 session；实例之间并行；平台开销接近直接使用 CLI。**

## 2. 对象与身份

| 对象     | 定义                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| Role     | 配置，不是实体：CLI + 模型 + effort + prompt + skills。稳定 Role ID；每次保存产生不可变 Revision                       |
| Instance | 频道成员，唯一 Instance ID（= principal）。创建时冻结 Role Revision 快照；同一 Role 可在同一频道多次实例化（用户自定） |
| Session  | 实例的原生 CLI session。一个实例始终延续同一个 session，不按任务、轮数或 token 自动轮换                                |
| Channel  | 协作记录与消息盒子；成员是实例，不是 Role。拥有一个平台创建的主工作目录与可选附加目录（见 §2a）                        |

- 修改 Role 不影响已有实例；实例显示"与当前 Role 配置不一致"。
- 实例可以切换模型和 effort（原生能力），不能切换 CLI。
- 移除实例：停止投递、安全终止当前执行、保留历史；重新加入同一 Role = 新实例。
- **旧的人格 Agent 模型被替代，evo 后端不再维护旧 Agent 路径。**旧数据不迁移（owner 2026-09-24 已退役旧环境并确认）。

## 2a. 频道工作区（owner 2026-09-26 批准）

- 频道拥有一个平台创建的主工作目录与可选附加目录；平台记忆按频道共享（§4，负责人 2026-09-26 裁定），不物化为实例或频道目录中的文件。
- 主目录：创建频道时由平台（Host）新建（默认 `~/.loom/channel-workspaces/<频道 id>`，根目录可配置），永不复用已有目录；建不出来（路径已被占用、不可写等）则创建频道失败并给出可诊断原因，不留下没有目录的频道；幂等重放返回同一频道与同一目录。绝对路径在创建时固定，此后改根目录配置不影响已有频道。它是该频道所有实例（含私聊）的 CLI cwd 与默认产物目录。频道归档、删除或实例重置都不删除它。（owner 2026-09-26 裁定：创建时建好，不惰性创建。）
- 附加目录：创建频道时可选 0 个或多个，由 Human 指定已存在的绝对路径目录；平台只校验，不创建、不删除；拒绝 Loom 数据目录与主目录根。
- 主目录与附加目录创建后不可修改。Host 在每次绑定刷新、启动、交付证据采集和文件浏览前复核两者仍是创建或批准时的那个目录（规范路径、不是符号链接、目录身份一致、不与 Loom 数据目录或主目录根重叠）；不一致即拒绝，不跟随新目标，不补建空目录。
- 已有频道与已有实例保持原 cwd（Claude/Kimi 按 cwd 定位会话，换 cwd 等于静默换会话）。
- 各 CLI 以原生机制获知附加目录；没有原生机制的 CLI 在常驻提示词里得到一行事实。不自动加载附加目录中的项目说明文件。

## 3. 调度与交流

- 不同实例并行；同一实例最多一条执行 lane，串行。
- 频道 `@实例` 是公开的定向请求，所有实例可见。**唤醒范围**（负责人 2026-09-27 裁定，有意偏离 Raft"@ 只是注意力标记"）：
  - 按整条消息的收件集合决定，不按 @ 在文中的位置切分。
  - Human 消息里的 @ 命中本频道启用的实例时，只唤醒被 @ 的实例（多个则各唤醒一次）；其他成员不产生 Inbox、Activation 或运行，稍后从频道读取。
  - 没有 @，或 @ 只落在非成员、Human、拼错或已移出的名字上：唤醒全体。
  - `@all` / `@所有人` 显式广播，即使同时 @ 了具体实例。
  - 代码块、行内代码、链接和邮箱里的 @ 不算点名；线程回复同一规则；客户端传入的收件人不能扩大范围。
  - 实例消息仍只按显式 @ 唤醒（链上限不变）。
  - **补读**：实例被唤醒时，唤醒正文在本次消息前附上它上次读取之后、本次唤醒之前的频道事件（共用 20 条 / 64 KiB 预算，本次消息优先，放不下的较早部分只报数量与序号范围）；隐式确认从补读段起点连续推进，不越过未呈现的事件。补读只陈述事实，不作为回复目标。
- **私聊**：右侧第三栏打开，使用私有 box；与频道共用实例 session，所以会影响后续上下文；忙时排队，不 steer 频道工作；其他实例看不到。
- **Steer**：频道配置项，默认开启，按 CLI 能力支持。只有 Human 消息可以 steer；其他实例的回复等空闲时再读。
- **Side**：从实例 session 分叉出的临时隔离会话，在第三栏打开；主 session 和其他实例不知道它的存在；可读记忆，禁止写记忆（由底层权限强制，不靠提示词）。
- **Fork**：持久复制实例上下文，在同一频道新增一个实例；系统告知新身份（"你是 No.2"）；不继承原实例的任务、收件义务、私聊访问权和凭据；已有私聊内容作为上下文随之复制。
- **故障恢复**：频道内报警；原生 session 文件还在 → 有限次数 fork 替代（保留 Instance ID）；找不到 → 用户选择是否用同配置新 session 读 box 重建，并记录上下文中断。永不静默换新 session。

## 4. 记忆

- 平台管理长期记忆，生命周期独立于实例和 session。
- Role、模型、session、频道、时间是平台自动填写的来源元数据，不是唯一归属边界。
- 先按权限确定可读范围，再按工作相关性检索；轻量索引 + 按需读正文，不全量加载。
- 记忆有修订、失效和删除；来源元数据只证明谁写的，不证明内容正确。
- 读写开关：频道设默认值，成员可覆盖，读和写分开；由底层权限强制：工具路径由 Kernel 在认证的 Worker 调用上检查，文件路径因记忆不物化为文件而不存在（见下方已裁定语义）。同 UID、full-access 运行的 CLI 直读数据库不在此强制范围内，是 status 登记的偏离，不是强隔离。
- 已裁定语义（负责人 2026-09-26 批准，依据 `~/.loom/reviews/2026-09-26-memory-research.md` 末尾裁定）：
  - 共享范围是频道：每条记忆属于一个频道，频道内有读权限的实例共享。实例在私聊（private box）里写入的记忆也属于该频道的共享记忆，不是私有记忆；出处记录经由的房间。
  - 只经显式工具写入（Worker `memory write/update`）：平台不从对话、私聊正文或 transcript 自动抽取，记忆不物化为文件。
  - 写入不蕴含读取：实例的变更只返回收据（条目、名字、修订、操作、状态），正文、描述和出处只能经受读开关约束的读取取得。
  - 并发写入：更新、失效、恢复、删除都带 `expectedRevision`，不一致即拒绝，不合并、不后写覆盖。
  - 实例与 Human 都可以失效和恢复（失效需理由）；只有 Human（频道管理者）可以删除。
  - 删除边界：删除后平台在线读取与检索不再能取得正文与描述（全部修订的正文置空、描述清空，当前投影同样清空；只保留名字、删除时间、删除理由与 tombstone 元数据；负责人 2026-09-27 裁定）；已冻结在 presented window 上的记忆快照也去掉该条描述；不追溯清理已进入 provider session、诊断、备份和 SQLite 物理残留（WAL）的副本。物理擦除需要另行设计，不在当前范围。
  - Side session 只读不写：判定点已存在，但 side 凭据尚未签发（S5 未接入），不是已验收能力。
  - 检索的频道过滤只保证输出范围：全文索引全库共享，排名统计可能受其他频道影响。

## 5. 上下文可见性

每个实例显示：每轮 usage（输入、缓存、输出）、上下文窗口占用、压缩次数。CLI 不提供的数据显示"未知"，不推算冒充实测。

## 6. 验收数字（对照原生 CLI 同一 session、同模型同 effort）

owner 2026-09-24 批准修订（原"回复前 ≤2、总输入 ≤2×"在两次完整生成下数学上不可达）。

| 指标                 | 目标                                                                    | 9/23 基线         |
| -------------------- | ----------------------------------------------------------------------- | ----------------- |
| 协议额外生成（整轮） | RAH 整轮生成数 − 原生整轮生成数 ≤ 1                                     | +2（check、收尾） |
| 回复前额外生成       | RAH 回复前生成数 − 原生整轮生成数 ≤ 0                                   | +1（check）       |
| 固定开销（相对原生） | 新 session 首次生成的输入差 ≤ +3k token                                 | 约 +11–13k        |
| 整轮总输入           | ≤ 2 × (原生整轮总输入 + 3k)，按"固定开销 + 每轮残留 + 业务差异"分解报告 | × 4.8–5.0         |
| 回复耗时             | 额外耗时 ≤ max(5 s, 原生耗时 × 15%)                                     | 原生 + 7–8 s      |
| 用量证据             | 采集完整；缺口或未知时判"证据不足"，不能判达标                          | 未采集            |
| 最终答案送达         | 100%（门禁样本内）                                                      | 首轮失败          |
| session 连续性       | 不静默换新；重启后续聊                                                  | 已通过（Codex）   |

“9/23 基线”列是 2026-09-23 首次门禁的实测（owner 2026-09-25 批准由“当前基线”改名；数值与预算未改），之后的实测见 [evo 现状](status.zh-CN.md)。

回复耗时规则：短任务按秒计（原生耗时约 33 s 以内时上限为 +5 s），长任务按百分比计（超过后上限为原生 × 15%），避免长任务的正常波动被误判。
口径（owner 2026-09-24 批准）：固定开销取新 session 首次生成的输入差；每轮协议残留单独统计（上下文逐轮增长之差）；两组工作路径不同（如读文件次数不同）造成的历史差异属业务差异，单独报告，不计入平台开销，也不得借此放宽固定开销上限。生成次数按业务生成与协议生成区分：原生完成同一工作所需的读文件等工具轮次不算协议开销。各运行时分别测、分别验收；需要调整目标时须给出不可消除的协议成本与实测，再由 owner 修订。

S1 完成后测一次；若离目标仍远，停下来重新评估架构，不继续叠加功能。

## 6a. 执行模型（owner 2026-09-24 确认，S2 实施）

- 能用 server 模式就用 server 模式：Codex `app-server`（unix socket）、OpenCode `serve`；Claude 用常驻流式输入模式；Kimi 用常驻 ACP。
- 每个实例一个热进程：实例创建时预热常驻运行时（只启动进程与就绪握手，不调用模型），daemon 启动后为最近活跃的实例同样预热；有消息时保持运行并连续处理；最后一次活动后保留一个空闲窗口（约 30 分钟）再回收；新消息到达时若已回收则重新激活，并按 session ID 恢复同一 session。不再每轮冷启动。预热计入全局与每 CLI 上限及启动限流，达到上限时不预热、不挤占其他实例；由 Human 在运行时设置中开关（owner 2026-09-27 批准），默认关闭（owner 2026-09-27 裁定：付费验证未测出稳定收益，设置文件缺省时不预热）。
- 已登记例外（措辞修正，语义不变；见 [status](status.zh-CN.md) 偏离清单）：Kimi 按 owner 选项 A（S2-c2）每轮冷回收，不常驻——kimi-code 会把请求排在引擎自发轮次之后并直接回 `end_turn`，无法证明本轮执行并结束；Claude 常驻默认关闭（需在 daemon 配置显式开启）。二者走每轮进程，不预热，其进程仍计入全局与每 CLI 上限。
- 绝不在一轮进行中回收，TUI 挂载期间不回收；在轮次边界可按内存、存活时长或 CLI 升级主动重启。
- 热进程设全局上限（按最近最少使用淘汰），沿用启动闸门；按进程组清理，启动时清孤儿；按"无进展"时长判卡死。
- Worker 凭据按轮次签发与撤销，不再依赖进程环境变量；轮次完成以原生轮次结束事件加进程状态为证。回收无损：事实在账本与 session ID 中。
- 同步挂载官方 TUI 是可选能力：Codex（`codex --remote … resume <thread>`）、OpenCode（`opencode attach --session`）可做，参考旧 rah 项目实现；Claude 等没有 server 模式的跳过。挂载期间由 Kernel 持单写者租约。

## 7. 工程原则（替代 main 的 Raft-first 原则）

- **以原生 CLI 为效率标杆**，Raft 源码只作参考，不再是默认移植来源。
- 能由代码强制的规则不写进提示词；异常说明只在出错时提供。
- 账本、认证、幂等、执行围栏等已验证的基础继续复用。
- 纵向 MVP：每个切片是能跑通的完整路径；低概率边界记录下来延后。
- 前端冻结在 main；evo 用 `apps/console` 简易控制台验收；阶段 4 再接回 main 的 UI。

## 8. 阶段 3 切片顺序

S1 每轮效率 → S2 session 生命周期与观测 → S3 私聊补缺 → S4 fork → S5 side → S6 平台记忆。
每个切片：测试先行 → 实现 → 控制台可见 → 提交并推送 evo；S1、S2、S6 结束时各跑一次付费门禁。

顺序变更（owner 批准）：S6 平台记忆已先于 S4、S5 实施。当前阶段为“收口 + 真实贯通验收”（owner 2026-09-27 裁定：在正式服务上用真实 CLI 走通 Role → 实例 → 频道多轮 → 私聊 → 记忆写读 → 重启续聊 → 控制台核对），不新增能力；之后由 owner 在 phase 4 窄 UI 切片与 S4 之间选择。
