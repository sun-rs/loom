# 输入放大根因与 Raft 私聊实测（P66）

## 结论

额外输入主要来自多次模型请求反复携带上下文，而非每次重新创建 session。P65 的 14 次请求对原生 6 次，是比首请求多约 2k 输入更大的乘数。协议的可选路径、重复投递与模型拆分工具工作共同放大；不能全部归罪于调度，也不能靠一次提示词修复宣布完成。

按用户授权新建 Raft Agent `TokenAudit0930`，同一 `gpt-6-luna / low` 做两轮私聊，另跑原生同题两轮。**Raft 也有明显放大，不能作为天然低成本模板。**本次 Raft 296,982 累计输入，原生 41,956，约 7.08 倍；未缓存 32,534 对 17,892，约 1.82 倍。首轮包含自动欢迎流程，不能推断稳定倍率，更不能拿私聊和 P65 多实例讨论直接排名。

## P65 的额外请求从哪里来

| 阶段             | 原生路径                | Loom 实际路径                                                      |
| ---------------- | ----------------------- | ------------------------------------------------------------------ |
| A 首次审查       | 一次工具读码 → 回答     | check → Git 探测失败 → 文件列表 → 读码 → progress 发帖 → 收尾      |
| B 首次核对       | 一次工具读两文件 → 回答 | check → 目录查询 → 读文件一 → 读文件二 → Git 探测失败 → final 发帖 |
| A 修订、恢复追问 | 各一次回答              | 各一次 final 发帖                                                  |

1. **重复确认入口：确认存在，诱因仍是推测。**两个首轮唤醒都已带正文和 `Reply: ... --final`，运行时也有文件根信息。常驻规则明确“Reply 时不先 check/read”（`packages/agent-host/src/standing-protocol.ts:148` 附近），但模型仍调用 check。不能说后端硬性强迫每轮 check。规则同时描述 check、无须回复时 check、消息缺失时 startup check 等分支，增加选择负担是合理假设，单样本不证明某句导致它。
2. **重复调用又重复正文：代码确认。**`packages/application-service/src/worker-application-service.ts:814–852` 首次 check 使用独立的 check cursor，缺省走 `replayDelivery: true`，不会因带正文唤醒已接收就压掉同一正文；`packages/agent-host/src/worker-message-check.ts:37–76` 格式化完整页后确认。P65 输出确实从 seq 1 回放，包含 room.created、成员配置与原问题。这里有恢复和 ACK 语义，不能简单跳过读取或让 Host 代模型 ACK。现状允许本来可省的 check 继续增加历史。
3. **工作目录与测试路径：观察确认，因果非唯一。**CLI cwd 是频道主目录，文件在附加目录；模型额外列文件并尝试 Git。文件本来已给名称和根路径，Git 探测不提供本题必要证据，两份固定文件也没有 `.git`。原生直接在快照目录读文件；这是业务环境差异，不能把全部定位成本称为协议必需。
4. **工具拆分：观察确认。**B 分两次读取两文件，原生合并读取。这多一次携带已读文件的请求，不是重复 Activation。平台应让批量只读更自然，不应为本题写专用审查流程。
5. **结束语义仍由模型选分支。**A 明知是交接仍显式 progress，随后多一次收尾。新默认 final 只解决“没写选项”，不能防止主动选择 progress；其余三轮 final 为一次生成，不应由此推导所有运行时都必须有两次生成。

按本次轨迹将 check、Git、目录列表、B 拆开的第二次读取、A 收尾标作额外请求，共八次，这八次输入合计 119,287；相对原生累计差额为 145,587，约 82% 可在这些请求上定位。**这只是请求账目分解，不是删掉步骤后一定节省相同数量的反事实测量**：读码内容、缓存和后续输入会改变。其余差额来自较大固定输入、重复消息及已有工具历史。A 首请求 10,866 对原生 8,810；续轮即使都是一次生成，输入仍约 1.31 倍。

“累计二三十万/七十万输入”不等于单次上下文有这么大：本次 Loom 单请求峰值约 21.6k，反复送入后累计 227.9k。缓存减少部分实际成本，但不消除模型请求次数和等待时间；美元费用未有可靠回执，不能按总输入比例直接宣称账单倍率。

## Raft 实测

- 本机 Raft Computer 1.0.32，Codex CLI 0.158.0。网页未登录；经本机用户 session 的官方 refresh 接口续期，再通过 `/api/agents`、`/channels/dm`、`/messages` 创建独立测试 Agent 与私聊。未导出或显示 token，未更改既有 Agent。
- 创建前核对实时模型目录，创建后核对配置，两轮原生 turn_context 均为 `gpt-6-luna / low`。`onboarding:false` 仍产生自动 `#all` 欢迎通知并启动一轮；这轮过程中私聊到达。不得把这当成干净的纯私聊冷启动。
- 两轮只读同一固定快照，第二轮不再读码。原生收到相同题面与绝对文件目录；没有多 Agent 接力。原生启动用现有隔离策略，Raft 保持产品默认 prompt/工具/技能设置，不能宣称 system 环境完全相等。

| 指标       | 原生首轮 | Raft 首轮（含欢迎） | 原生续轮 | Raft 续轮 |
| ---------- | -------: | ------------------: | -------: | --------: |
| 生成次数   |        2 |                   8 |        1 |         3 |
| 累计输入   |   25,160 |             199,371 |   16,796 |    97,611 |
| 未缓存输入 |   17,224 |              30,411 |      668 |     2,123 |
| 首请求输入 |        — |              22,154 |   16,796 |    31,748 |

Raft 首轮：读 MEMORY → 尝试读欢迎消息 → check → 读私聊 → 空命令 → 读两份代码 → 发帖 → 收尾。欢迎、空命令不应算作日常必然开销。第二轮：读私聊 → 发帖 → 收尾，三次均携带约 32k 上下文。两轮同一 session，首轮回复约在 Human 发言后 26.7 秒落库；第二轮回复发到该私聊消息的 thread，已从 thread API 核实，不是漏回复。

Raft session 的第一段 developer 消息 38,629 字符，Loom P65 为 8,326；包含的平台规则及技能等环境不同，不能将全部字符差视为同一职责的纯协议差。Raft 正文不是直接随本次提示送达，实际输入为 inbox notice，模型需 read/check 获取内容；Loom 此样本已带正文，却仍选择 check。Raft 内置记忆、启动恢复、工具发帖和原生收尾也会累积输入，因此“完全模仿 Raft 就能消除成本问题”没有实测依据。

测试结束后仅停止新建 Agent（保留配置与私聊历史），没有停 Raft Computer 或其他 Agent。两组共 14 次生成、338,938 输入，协调者开销和美元费用未知。原始取证目录 `/private/tmp/loom-raft-dm-20260930`，[脱敏证据](evidence/2026-09-30-raft-dm-cost.json)。本次未修改 Loom 产品代码、未重启服务、未提交/推送。

## 下一步应收口的设计

1. 明确带正文唤醒、主动补读、故障 replay 三条路径的职责；优先评估首次 check 对已送达正文给精简引用的可行性，必须保留范围、缺失事件、显式 replay 与消费者 ACK，不能借优化放宽围栏。该改动只减重复体积，不保证模型少一次生成。
2. 核查通用工作区上下文能否清楚区分 cwd 与附加文件根，减少无效探测；保持测试两臂路径条件一致再评估，不加场景专用提示词。
3. 保留 final 的低开销路径，进一步区分“本次答复已交接”与“整个合作任务未完”。默认参数解决不了主动 progress 的选择问题，不建议为了节流直接杀掉合法中途进度。

先做以上设计/免费复现，不再靠扩大付费措辞样本或降低门禁指标宣称问题已解决。
