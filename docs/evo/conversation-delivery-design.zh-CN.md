# 频道与 Task 消息列：唤醒和差额读取

负责人 2026-10-02 批准重新设计并落地。本设计修订目标合同 §3 的“整个频道差额”规则。

## 产品合同

Task 是频道内的持久对话分区；负责人、状态与交付是附加信息。能读取不等于自动订阅。
频道正文默认参与；消息列普通投递按关注关系，直接 @ 可加入关注，自己发言加入关注，退出关注停止后续普通通知。Task 创建时的负责人、协作者、审核人、实例创建者，以及后续认领／指派者加入同一关注表；不另建 Task 通知订阅。schema 81 对历史成员补齐缺失的关注记录，已有取消关注优先，不回填任何已读证据。Task 不因闲置或完成而关闭讨论。实例自己的消息不唤醒自己。实例作者仍遵守显式 @ 唤醒规则；本批不改成实例互相广播。Human 在消息列不 @ 时只通知该列关注者；@all 保留显式频道广播语义。

## 唯一所有者与三种位置

Kernel owns Room ledger、关注关系、投递和读取证据。不得新建调度队列。

1. Room delivery cursor：一次消费者扫描/确认到哪个账本位置，用来结算 Activation；不代表所有消息列都被读过。
2. Target read position：实例+Room+消息列（频道正文使用独立 key）已经读取的位置，复用 worker_target_read_positions。
3. 逐消息呈现凭据：复用 worker_message_presentations，用于精确覆盖，不能由最高序号猜测。

差额不是时间差，而是每个目标内 `(lastRead, frozenHead]` 的消息集合。自动上下文只包含频道正文、已关注消息列及本轮明确投递的目标；其他消息列保留可搜索/显式读取，但不自动灌入。

## 读取和确认

- 唤醒正文和 message-check 共用 Kernel 自动选择规则；不能只过滤唤醒却由 check 全量灌回。
- 显式 room-read/message-read/search 保留原权限及分页，不因未关注拒绝读取。
- 每个目标独立下界；新关注旧消息列不能用频道已读位置跳过它的未读内容。首次窗口有界，根消息/历史按需补读，不承诺全部历史一次灌入。
- 窗口冻结选择范围及下界，重呈现不随关注/读取位置变化，避免 digest 漂移。后续轮次应用新的关注状态。
- 不相关账本位置可作为自动投递不适用项越过，但绝不能写入“正文已呈现/已读”的凭据。只对实际返回正文记逐消息证据。
- message-check 在分页和字节预算之前过滤无关消息列；没有正文的过滤尾段可推进扫描位置，不产生正文读取凭据。Task 后续状态事件随目标选择，Task 创建信息仍是频道事实。
- 超预算说明数量和序号，保留分页补读路径；未知业务事件不静默丢弃。Host 送达不构成 ACK。Task 完成仍需显式动作。

## P94 续办修复：执行认领与业务幂等分开

同一个 Activation 可因失败而创建新的 RunAttempt。旧设计的默认认领／启动幂等键只含 Activation，因此新 Run 重新认领时拿到旧成功事件，过期 lease 没有续上；后续 progress/submit 正确拒绝无有效执行权的操作。

最小修法由 Kernel 命令身份解析器负责：仅 claim、start、batch-claim、update-status(in_progress) 的默认键追加认证 RunAttempt ID。同 Run 的网络重试仍得到相同回执；显式键仍精确重放，不把旧回执偷偷变成续租操作。create/convert/progress/submit 等业务操作的键不变，防止换 Run 重复创建、重复交付。状态入口遇到已过期的 claimed/in_progress 时，在原事务内经过原有 claim 和 start 所有者重新获取执行权；状态相同不再等于租约有效。

旧租约尚未过期时，仅允许同实例、同 Activation 的后继 Run 在前次认领 Run 已终止后重新认领；同 Run 换键仍冲突，不开放抢占。

不删除租约检查，不增加队列或表，不修改 Task 长期负责人、对话历史、session、ACK 或业务完成条件。旧 Run 不可写、其他负责人不可抢占、新事实仍需补读。同一活跃 Run 的续租继续由现有 heartbeat 承担；显式复用旧键表示重放旧操作，不承诺续租。此批不修改该语义或用新提示词掩盖它。

回归先复现同 Activation 换 Run 后的旧回执，再验证过期重新认领→启动→进度→提交、精确重试不重复事件、旧 Run 拒写；另覆盖状态入口过期恢复及业务键跨 Run 保持稳定。真实 CLI 验收另列，本批免费测试不替代它。

本次修复的免费验证：专项 15 项通过。全量 `npm run check` 后端首次 2753 通过、22 跳过、2 失败：一项热 Codex 测试等待 running turn 超时，单独复跑通过，未改其时限或断言；另一项 daemon 旧断言要求跨 Run 仅一次 claim/start，现明确改为每个 Run 各一次执行认领／启动，并保留 create/progress/submit 各一次的精确断言、增加两个 claim 的不同 Run 归属检查，整个 daemon 文件 21 项通过。首次失败记录保留，不宣称全量首次全绿。被 `check` 的短路跳过的 Web、控制台、parity、正式浏览器政策、双边截图策略及效率门禁单测已另行执行通过；最终类型、格式和 diff 检查通过。未执行付费 CLI，本次运行次数、token、实际 Task 续办结果仍待有界真实验收。

## 2026-10-06：模型投递显示精简

Host 的 `worker-read-render.ts` 继续单独拥有 bodied wake 的文本投影。连续事件只有完整 Room ID、完整 Thread ID 与显示目标均相同时，才可使用一个 `Target:` 标题；单条及 UTF-8 字节没有严格减少的分组保留逐条目标。不按短引用合并，不重排事件，不跨 `Since your last read` / `For you` 分区，每次渲染重新声明目标。正文、Room seq、作者、消息引用、mentions、附件、Reply context、notice、重试及恢复信息保持原语义。

仅 `instance.created` 投影隐藏顶层 `provisionEventId` 和 `requestDigest`；完整实例及其他字段保留，其他事件不删字段。Kernel 事件、完整 Worker 响应、contentDigest 和 ACK 所有权不变；原生 session 的既有历史不改写。这是本地显示实现，无上游代码复制。实际字节、免费链路、自动检查及部署状态分开记于[本批证据](evidence/2026-10-06-compact-wake-projection.md)，不由文本压缩推断效率达标。

## 明确请求的单跳回复返回（2026-10-12）

Owner在“模型回复后由Loom接收并通知相关成员”的讨论后同意继续。Kernel拥有收件推导，Host仅提交认证final；不增加适配器队列、模型调用或工作流。目标边界见[合同§3](target-contract.zh-CN.md#3-调度与交流)。

对于频道顶层、无附件、唯一明确点名来源，当前Run的已送达正文记录与原请求者同代认证写入共同证明返回资格。普通native final和Worker final均在原消息事务中记录`replyReturn: {sourceEventId, participantId}`，派生`reply`原因的Inbox／Activation／Outbox，沿用成员权限、忙时排队及频道链上限。消息正文与canonical mentions保持原样，来源元数据证明路由，不能代替已读、任务完成或内容正确性。

显式点名／广播优先；返回不会再生成自动返回资格，已有显式回信不再补投。多来源、线程、附件、私有box及缺少当前运行送达证据维持原明确收件方式。普通Human新事实仍可能hold，held不产生任何返回投递。规则不识别“请继续”等语义，不内置实现者／审查者角色。当前实现不扩展为全员自动讨论。
