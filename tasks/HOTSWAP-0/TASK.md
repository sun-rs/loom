# HOTSWAP-0 (phase 1: audit + design + harness): upgrade loom without disturbing running sessions
Requirement from super: like hc and the HC Mac app, which can be updated at any time without affecting running TUIs/terminals, loom must be able to upgrade itself (loomd, CLI, loom-pty, OAR runtime glue, schema) while Leaders/Auditors/workers keep running. This is essential for loom to iterate on itself.
1. Study how hc achieves this (public docs/behaviour only; observe with hc --help, process tree, which process owns PTYs; do not modify hc) and how Orca handles updates while terminals run (TUI-ORCA-1 is also checking; read its notes if present).
2. Audit loom_new today, by experiment in your own test dir: what happens to (a) TUI sessions (hc + loom-pty), (b) headless workers (OAR runtime processes — are they children of loomd?), (c) pending deliveries/waves, when you: restart loomd; replace loomd code and restart; replace loom-pty code (running wrappers keep old code? control protocol compatibility?); change SQLite/journal schema; upgrade @botiverse/oar. Record evidence.
3. Design: process ownership (e.g. headless session hosts detached from loomd and re-attachable, or resumable via native session ids), versioned control protocols with old/new coexistence, forward-compatible storage migrations, drain/handoff procedure, 'loom upgrade' command semantics, rollback. Keep it thin; reuse OAR resume/attach where it exists.
4. Build a test harness (scripts + tests under tasks/HOTSWAP-0/ and exp dir) that runs a live wave + TUI leader and performs each upgrade step, asserting zero lost/duplicate deliveries and no session interruption. Phase 2 (implementation) follows after FIX-2A lands, since FIX-2A currently owns daemon/ and inbox/.
