# HOTSWAP-0 无中断升级设计

## 进程与版本归属

- 每个项目由一个 loomd 管理索引、收件箱、波次、通知和投递调度。终端和无头会话各有独立于 loomd 的宿主。TUI 沿用 hc 持有外层 PTY、loom-pty 持有内层 PTY 的结构，保留现有的窗格身份、控制套接字和请求簿。
- 无头会话增加一个轻量、独立进程组的会话宿主。每个会话固定一个 Loom/OAR 发布目录。宿主自行打开 OAR Session，持有 provider 的 stdio 和 OAR 订阅，继续运行工具与子任务。loomd 经项目私有 Unix 套接字查询状态、发送控制请求及拉取事件。宿主不直接写项目的 SQLite、inbox 或 relay 状态。显式 `loom stop` 关闭那个会话的宿主，loomd 换代只断开连接。
- 启动时先持久化 Loom 地址和启动意图，再领取唯一的会话启动锁。绑定记录保存发布版本、套接字、宿主 incarnation、PID 与进程启动时间、原生 session ID 和事件日志位置。重连校验这些身份。启动返回丢失时按启动意图重新查找已有宿主。只有核实旧宿主已退出，才允许创建下一 incarnation。
- 先接回活宿主。宿主已死时，复用当前 `runtime.session(installation, { cwd, resume: sessionId, ... })`，保留记录的 cwd、模型和启动选项，再验证原生 ID。按厂商能力区分原有进程重连、从持久会话重新打开、无法恢复三种结果。Codex 的 stdio app-server 和 agy 的 ACP `session/load` 都需要按各自实现验证，原生 ID 相同不足以认定正在执行的轮次延续。恢复时独立对账已提交输入和原生轮次边界。
- 首次部署前查明项目是否还有由旧 loomd 直接持有的 headless Session。有活动会话的项目保留旧 daemon，报告阻塞的会话并等其退役。待具备独立宿主后，后续版本可并行运行。安装位置提供稳定的 CLI 入口和按版本固定的代码、依赖、原生模块及 hook 入口。存活的宿主、包装器和脚本继续使用同一发布目录，分别在最后一个引用退出后回收。状态展示旧版本占用的会话和版本。
- 无需在第一版实现 PTY 文件描述符移交、Node 热重载或跨进程迁移 OAR Session。验收边界是连续运行同一原生进程和轮次，以及客户端可恢复的短暂 RPC 空窗。

## 控制和投递

- 沿用 loom-pty 的 `hello`、能力列表及 incarnation 校验。旧 wrapper 无 `hello` 时以原始方法集作为 v0。身份错误、响应超时和套接字故障分别处理。给无头宿主和 loomd RPC 补版本与能力协商。新 daemon 先验证项目所有活宿主的协议，发布期默认共用原方法集。允许字段扩展，有破坏性变更时通过能力协商和上一主版本适配维持双向兼容。新 CLI 与旧 loomd 在升级期间仍能用原命令。
- 项目单写者锁防止两个 loomd 调度。交接使用持久世代号，宿主核验会话 incarnation 和控制者世代号。旧世代的在途请求按已记下的 ID 对账，停发后才交给新世代。宿主与 wrapper 的控制端点使用只对当前用户可读写的目录和套接字。
- 继续使用 inbox 的投递 ID，以及 wrapper 的文本摘要和请求簿。无头宿主在写入原生进程前，持久记录 ID、动作、内容摘要和目标轮次。相同 ID 与内容返回已有状态，变更内容冲突。恢复时从日志和原生收据对账。已确认输入完成之前保留原收据，传输失败或只知可能提交的输入留在 `uncertain` 并按现有策略升级。只有有证据表明未提交时才允许重发。原生接口没有可靠去重或原生确认时，交付协议无法承诺任何崩溃点的严格 exactly-once。
- 原生事件保留会话 incarnation、stream ID、递增序号、投递 ID 和原生 turn ID。宿主落盘后再暴露读取进度。新 daemon 以最后的持久游标补读，按事件 ID 幂等推进 inbox 和 relay。保留波次的注册、封批截止时间、迟到补投和 outbox 投递 ID，交接期间发布过的汇总通过同一 ID 对账。已受理 RPC 可用其原 ID 重试。空窗内未得到受理的调用需要明确可重试结果。

## 存储和回滚

- SQLite 用 `PRAGMA user_version` 区分模式版本并记录组件兼容范围。在项目单写者锁下做事务性迁移。先把读取和更新路径改为显式列投影，随后才向 `sessions` 加可空或带默认值的字段。旁表使用独立命名，保存会话键。发布前从仍会运行的上一版本实测查询、插入和更新。索引数据库、inbox、relay 是同一业务事实的不同投影，升级不能只恢复其中一个。
- 宿主证据日志用追加记录和版本字段，老读者至少能保留并跳过不认识的扩展。现有快照文件继续用原子替换，未知字段要能往返保留，再启用新写入。新增必读记录用并行流或旧格式投影。日志恢复识别尾部不完整行、流世代切换和重复序号。新读者应从原游标跨版本读取，运行中不在原地重写活日志。
- 升级采用先扩展、再切换、后收缩。兼容窗口中同时保留两代读写能力。只有前一版本已退役、回滚窗口关闭且完成独立的迁移后才移除旧结构。切换失败时使用同一个项目状态和上一版发布目录重启控制面并补读交接期间的日志。回滚不把存活会话写入的日志、收据或队列恢复到旧时间点。碰到不可逆模式变更，第一版预检就拒绝在线升级。

## `loom upgrade` 命令

建议 `loom upgrade --project ABS --to RELEASE [--check] [--json]` 使用已准备的本地发布目录。单独的 `loom upgrade --project ABS --status --json` 查询一次升级与当前宿主版本。`--rollback` 对最近的兼容发布发起反向交接。

1. 校验发布版本、依赖、平台和摘要，保存升级 ID 和上一个发布指针。只读预检当前写锁、活宿主协议、磁盘格式、迁移事务和可回滚窗口。`--check` 输出可切换版本、继续挂在旧版的会话及阻塞原因。
2. 旧 daemon 进入 drain，拒绝新的变更 RPC，并等待在途 RPC 把受理、拒绝或不明状态写完。刷盘并保存待投递 ID、活宿主身份和游标，停止创建新的投递尝试。正在执行的轮次继续运行并追加证据。旧 daemon 释放写锁和 RPC 套接字。
3. 新 daemon 获得锁与下一世代，运行兼容迁移，逐个验证宿主身份和能力后补读日志、对账已受理请求及 relay outbox。完成接管与健康检查后发布就绪，原子推进活动发布指针，恢复接受新变更。已有会话保留原宿主版本，新会话由新版本启动。
4. 升级记录区分预检、排空、接管就绪和提交。重试同一目标时继续未完成的步骤。新 daemon 构建或探活失败时把指针退回，并由上代在同一锁和下一世代下接管。CLI 报告升级是否成功、回退是否成功、各宿主版本及阻塞会话。已提交后收到显式回滚请求时走同一路径。

## 第二阶段验收

将本卡夹具接入正式 `loom upgrade` 的交接阶段，在排空、宿主收据落盘、切换锁持有者、完成投递前后各注入一次退出。保留主动重启和 SIGKILL 对照，覆盖同一兼容窗口中的两代 loom-pty/OAR；分别验证旧 CLI 连新 daemon、新 CLI 连旧 daemon、未知能力拒绝、扩展 SQL 的读写及升级后的原地回滚。对每个投递比较 inbox、原生输入记录、原生 turn ID 和完成结果，对每波比较 outbox 与 Leader 的原生提交次数。任何重放、丢结果、已接管轮次退出或原生 PID 变化都应使连续性测试失败。厂商矩阵再覆盖真实 Claude、agy 以及相应的失联恢复语义。
