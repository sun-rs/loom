# RESEARCH-ORCH-0｜一个协调者如何带多个执行者

调研截点为 2026-11-25。loom 的前提是人类 Super 下设同级 Leader 和 Auditor，每项目由主要运行在 headless 模式的低成本 Worker 执行。任务卡给出的历史观察是两名协调角色合占 25%–40% 支出，目标是 Worker 约占 90%。建议首轮用 **1 名 Leader 带 3 名活跃 Worker，另有 1 名按需唤醒的同级 Auditor**。把状态同步交给运行时，把模型回合留给分派、决策和验收。1:3 是试运行起点，90% 是待验证的预算目标。 [任务卡](./TASK.md) [Claude Code 团队规模](https://code.claude.com/docs/en/agent-teams#choose-an-appropriate-team-size) [Orca 编排](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/cli/orchestration.mdx) [Antigravity Swarm](https://antigravity.google/docs/swarm) [Multica Squads](https://multica.ai/docs/squads)

## 能复用的做法与常见失败

1. **按独立验收单元拆分，并把写入所有权明确到文件或接口。** 同一公共接口、迁移顺序或锁文件留给一个责任人。独立 worktree 能隔开未合并的写入，合入处还要判定行为和依赖冲突。同文件写入、模糊目标、过细粒度都会制造返工。Cursor 的共享锁实验还说明认领协议宜由程序处理。 [Claude Teams](https://code.claude.com/docs/en/agent-teams) [Cognition 工程总结](https://cognition.com/blog/multi-agents-working) [Antigravity Teamwork](https://antigravity.google/docs/teamwork/) [Cursor 实验](https://cursor.com/blog/scaling-agents)
2. **派发写清目标、证据和边界，交付用短摘要加可直接读取的产物。** 短消息使 Leader 能快速决定下一步，分支、diff、测试证据和原日志能由需要的人独立取回。层层转述会丢信息；全轨迹自动灌入每轮协调会增加上下文；只有退出码或完成宣告也无法验交付。 [Anthropic Research](https://www.anthropic.com/research/multi-agent-research-system) [OpenAI Codex](https://openai.com/index/introducing-codex/) [Antigravity Artifacts](https://developers.googleblog.com/build-with-google-antigravity-our-new-agentic-development-platform/) [Devin Fusion](https://cognition.com/blog/local-fusion)
3. **让可独立推进的工作异步跑，由运行时投递和对账。** 必须汇合时只等该依赖集合。过量进度消息会产生重复回合，等待整批会被慢尾拖住。异步也会遇到重启、事件延迟和结果竞态，需持久状态、租约、幂等及有边界的重试。 [Anthropic Research](https://www.anthropic.com/research/multi-agent-research-system) [Orca](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/cli/orchestration.mdx) [Paseo](https://github.com/getpaseo/paseo/blob/main/docs/agent-lifecycle.md) [Symphony](https://github.com/openai/symphony/blob/main/SPEC.md)
4. **独立验证优先放在已形成证据的时点。** Factory 与 Antigravity 在有实现或里程碑证据后验证，Cognition 报告干净上下文的 reviewer 可发现实现者漏掉的问题。 reviewer 先看验收约束、diff 和可复跑证据，发现具体问题再取原文。频繁无门槛往返会扩范围或陷入审查循环。现有资料支持独立验证的价值，仍缺同级 Auditor 持续打断 Leader 的对照实测。 [Factory 架构](https://factory.com/news/missions-architecture) [Swarm 验证](https://antigravity.google/docs/swarm) [Cognition 互评经验](https://cognition.com/blog/multi-agents-working) [MAST 研究](https://arxiv.org/abs/2503.13657)
5. **规模靠边界和判定标准，费用靠按角色测量。** 工作高度相依时，增加角色会重复探索、扩大通信和验收成本。大规模编程实验说明明确可跑的判定更重要。研究 token 倍数、Fusion 的任务总价差、产品配额、编译器实验总价分别回答不同问题；调查范围内没有可直接移植给 loom 的 Leader/Auditor/Worker 美元分摊。MAST 分析 150 条轨迹，归纳 14 类失败，归在规范设计、协作对齐及验证/终止三组。 [Anthropic Research](https://www.anthropic.com/research/multi-agent-research-system) [并行编译器](https://www.anthropic.com/research/building-c-compiler) [Fusion 基准](https://cognition.com/blog/local-fusion) [Jules 配额](https://jules.google/docs/usage-limits/) [MAST](https://arxiv.org/abs/2503.13657)

### 验证 90% 目标

- **先固定计算口径。** 设 `W` 为 Worker 模型美元成本，`C = Leader + Auditor`，目标 `C/(W+C) ≤ 0.10` 等价于 `C ≤ W/9`。任务卡 25%–40% 对应 `C/W ≈ 0.33–0.67`。若 Worker 的绝对费用固定，协调端绝对费用要下降约 67%–83%。对 API 记输入、输出、缓存读写和实际美元。对订阅记可见用量，估值与账单分列。费用未知的运行另记覆盖率。 [loom 基线](./TASK.md) [Anthropic 成本口径](https://code.claude.com/docs/en/costs) [Multica 分项](https://multica.ai/docs/analytics)
- **按独立程度分层做配对试验。** 对同类小块、跨模块和高风险工作分别选同等输入、验收及模型档位，固定 Worker 数，先对照逐条唤醒和事件合批，再在合批条件下比较全程 Auditor 和阶段门 Auditor。保留单 Worker 基线；再比较 1:3 与 1:5。每个条件先收 10 项作为试运行，公布样本量、P50/P90、失败和重派成本。审查策略用同一份 CI/验收，抽样盲评，以便估计漏检。 [loom 基线](./TASK.md) [Anthropic 评估方法](https://www.anthropic.com/research/multi-agent-research-system) [Factory 验收](https://factory.com/news/missions-architecture)
- **先验证可靠性，再调预算。** 复盘同时查看每项验收通过的模型及全成本、首次通过率、复开率、P90 交付时延、事件交付延迟、唤醒后无动作比例、Auditor 的阻塞命中和误拦。初始放行条件为阶段门前高风险漏检零例，P90 较同层基线增加不超过 10%，质量及单位成本不退化。样本不足时继续观察；用过于严格或宽松的门槛造成异常时，用可复跑的失败案例校准。这里的阈值和样本起点属于弱证据试验设定。 [Anthropic 生产评估](https://www.anthropic.com/research/multi-agent-research-system) [MAST](https://arxiv.org/abs/2503.13657) [loom 基线](./TASK.md)
